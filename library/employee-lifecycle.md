# Joiners role changes and departures

Access is a lifecycle, not a one-time setup task. A VC firm's employees, contractors, advisers, temporary staff, and external collaborators may each need a different sponsor, data boundary, and end date.

## Intake and authority

Accept personnel changes from an agreed authoritative source. Record the sponsor, role, start or change time, expected end date where relevant, devices, required applications, and approvals. Verify unusual or urgent requests through a known channel. A forwarded message is not automatically sufficient authority to grant sensitive access.

Use [identity and access policy](../documentation/policies/identity-and-access.md) to define who requests, approves, implements, and verifies each change.

## Joiner acceptance

Before the person starts, prepare the approved identity, device, authentication enrollment, application access, and support instructions. Use role-based defaults but confirm restricted workspaces separately. Investment committee, personnel, fund, and investor records should not become broadly accessible simply because someone joins the firm.

Acceptance means the new user can complete the intended work from a compliant device, understands where to request help, and cannot access an excluded test resource. Record which applications were checked and any outstanding approvals.

## Role changes

Compare the current access population with the new role. Include direct assignments, inherited groups, external workspaces, shared links, delegated mail/calendar access, service ownership, and mobile or local copies where relevant.

Where overlap is needed, assign a reason, approver, expiry, and removal check. Revisit access when a person changes fund responsibilities or leaves a restricted project even if their job title stays the same.

## Departures

Coordinate the effective time with the personnel owner. Preserve required records and holds before deletion. Revoke sign-in and relevant sessions, direct application accounts, remote access, guest memberships, delegated permissions, and authenticators through supported controls. Transfer service ownership and rotate shared secrets the person could access where needed.

Track devices, backup access, repositories, automation owners, domain administration, billing ownership, and emergency procedures. The identity provider may not control all of them.

## Verify and resolve exceptions

For every required action, record submitted state, completed state, verifier, evidence, and exception. If a provider controls the application, obtain a specific completion record. Do not mark an unknown as done because the checklist's deadline has passed.

Run a fictional joiner, a mid-project role change, and an urgent departure through the process before relying on it. The [JML review workflow](../n8n/README.md) can help check completeness of structured records; it does not perform revocation or supply missing authority.

Use the [lost-device procedure](../documentation/procedures/lost-device-response.md) when an unavailable device introduces a separate exposure question.
