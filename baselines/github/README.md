# GitHub: a baseline for technology operations

I would start with the two paths a small firm cannot afford to lose control of: who can change what runs in production, and which credentials can act without a person watching. In a GitHub organization used for internal tooling, automations, and AI agents, those paths run through owners, tokens, workflows, installed apps, and the agents that open pull requests. A useful baseline protects them while still letting engineers, contractors, and agents ship changes.

This guide is a proposed operating standard. [Twenty control assertions](desired-state.json), the [evidence worksheet](evidence-worksheet.csv), and a [risk assessment template](risk-assessment.csv) make it reviewable. They are not settings to import, and the [local assessment tool](../README.md) compares reviewer-recorded assertions; it does not connect to GitHub, read an organization, or verify evidence. The linked GitHub documentation was reviewed on **2026-09-20**; each control carries its own source and a review gate that names the plan or product it depends on.

## Make the scope explicit

Before rating any setting, record the plan (Free, Team, or Enterprise Cloud), which Advanced Security products are licensed (GitHub Secret Protection and GitHub Code Security are the current products behind secret scanning and code scanning on private repositories), the Copilot plan, the identity provider, and the repositories in scope by class: production, internal tooling, automation, and agent-operated. List every automation and agent with the credential it uses and the repositories it can write to. Keep the actual details outside this repository.

Use three example populations when designing a pilot: an organization owner, an engineer who maintains automations, and an AI agent or service account with write access to at least one repository. Include an outside collaborator if that is an actual requirement. The purpose is to expose a business dependency before an organization-wide restriction does.

## Membership and roles: controls 01–03

GitHub documents that owners have complete administrative access and recommends at least two, because a single unreachable owner can make the organization inaccessible. I would keep the owner list short, individually accountable, and paired with a private succession record. [Roles in an organization](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/roles-in-an-organization), [ownership continuity](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/maintaining-ownership-continuity-for-your-organization).

The member privileges page decides the default. A base permission of No permission or Read means repository access is granted deliberately through teams. Restricting visibility changes to owners closes the most common route to an accidental public repository. Restricting members to private-only creation is documented for Enterprise Cloud; on Team, the choice is between allowing both visibilities and public only, so the visibility-change restriction carries more weight. [Base permissions](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/setting-base-permissions-for-an-organization), [repository creation](https://docs.github.com/en/organizations/managing-organization-settings/restricting-repository-creation-in-your-organization), [visibility changes](https://docs.github.com/en/organizations/managing-organization-settings/restricting-repository-visibility-changes-in-your-organization).

Outside collaborators sit outside base permissions and outside SAML. Give each one a sponsor, purpose, minimum repository set, and end date, then review on a schedule. Owner-only invitation is an Enterprise Cloud capability; a Team organization relies on the review. Removal deletes private forks but not local clones and does not lower the paid seat count. [Adding outside collaborators](https://docs.github.com/en/organizations/managing-organization-settings/setting-permissions-for-adding-outside-collaborators), [removing an outside collaborator](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-outside-collaborators/removing-an-outside-collaborator-from-an-organization-repository).

## Authentication and credentials: controls 04–07

Requiring two-factor authentication removes outside collaborators who have not enrolled and blocks members until they do, so notify people first and confirm every owner has enrolled. The optional secure-methods setting excludes SMS. [Requiring 2FA](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-two-factor-authentication-for-your-organization/requiring-two-factor-authentication-in-your-organization).

SAML single sign-on and SCIM are documented for Enterprise Cloud only. Enforcement removes members who have not authenticated through the identity provider, so test with enforcement off, then use a synthetic leaver to prove SCIM deprovisioning works before trusting it. On Team, record this as an unsupported native control and rely on the 2FA requirement, membership review, and token policy. [Enforcing SAML SSO](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-saml-single-sign-on-for-your-organization/enforcing-saml-single-sign-on-for-your-organization), [SCIM for organizations](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-saml-single-sign-on-for-your-organization/about-scim-for-organizations).

Personal access tokens are where automations and agents usually start, and where organization-wide access leaks. The token policy can require owner approval for fine-grained tokens, cap their lifetime, and restrict classic tokens from organization resources. Only fine-grained tokens can be listed and revoked in the organization view; classic tokens are invisible there, and changing the policy does not revoke tokens already issued. [Token policy](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization), [reviewing tokens](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/reviewing-and-revoking-personal-access-tokens-in-your-organization).

SSH certificate authorities let an Enterprise Cloud organization issue short-lived Git certificates instead of trusting long-lived personal keys. Requiring certificates also blocks HTTPS authentication to organization repositories, and issued certificates cannot be revoked, so inventory every automation before enabling the requirement. [About SSH CAs](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-git-access-to-your-organizations-repositories/about-ssh-certificate-authorities), [managing SSH CAs](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-git-access-to-your-organizations-repositories/managing-your-organizations-ssh-certificate-authorities).

## Repository protections: controls 08–09

Rulesets are the current mechanism for protected branches. GitHub documents them for Team and Enterprise plans, and the overview describes organization-level rulesets that target many repositories for Enterprise; check the actual plan to see whether one ruleset can cover every production repository or each repository needs its own. The acceptance test is a synthetic writer who cannot push to the default branch directly and whose pull request waits for an approving review and passing checks. [Creating organization rulesets](https://docs.github.com/en/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization), [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

Blocking force pushes and deletions protects history. Requiring signed commits is only enforceable once every committer, including automations and agents pushing from a runner, has a verified signing route; commits made in the web interface are signed by GitHub, but a bot pushing from a workflow is not. Review who sits on the bypass list and use rule insights to see who used it. [Commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), [managing rulesets](https://docs.github.com/en/organizations/managing-organization-settings/managing-rulesets-for-repositories-in-your-organization).

## Code security: controls 10–12

Secret scanning and push protection run at no charge on public repositories; private and internal repositories need GitHub Secret Protection on Team or Enterprise Cloud. Security configurations apply the settings across the organization. By default anyone with write access can bypass push protection with a stated reason, so decide who should hold bypass privileges before the first blocked push surprises an engineer. [About secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning), [push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection), [enabling security features at scale](https://docs.github.com/en/code-security/securing-your-organization/introduction-to-securing-your-organization-at-scale/about-enabling-security-features-at-scale).

Dependabot alerts and security updates can be enabled for all eligible repositories in the organization; they depend on the dependency graph. An alert without an owner is not a control, so record who triages and within what window. [About Dependabot alerts](https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts), [configuring alerts](https://docs.github.com/en/code-security/dependabot/dependabot-alerts/configuring-dependabot-alerts), [security updates](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/configuring-dependabot-security-updates).

Code scanning on private repositories requires a GitHub Code Security license, and default setup runs through Actions and consumes minutes. Scope it to repositories that ship to production or handle firm data rather than every experiment. [About code scanning](https://docs.github.com/en/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning), [default setup](https://docs.github.com/en/code-security/code-scanning/enabling-code-scanning/configuring-default-setup-for-code-scanning).

## Actions security: controls 13–16

The organization Actions settings page sets the ceiling for every repository: which actions and reusable workflows may run, whether fork pull request workflows need approval, whether the default `GITHUB_TOKEN` is read-only, and whether Actions may create or approve pull requests. GitHub documents pinning to a full commit SHA as the only immutable way to reference an action. Note that `pull_request_target` workflows are not gated by fork approval. [Organization Actions settings](https://docs.github.com/en/organizations/managing-organization-settings/disabling-or-limiting-github-actions-for-your-organization), [secure use reference](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).

Environments put a human between a workflow and production: required reviewers who cannot approve their own run, deployment branch restrictions, and secrets that only jobs referencing the environment can read. Environments on private repositories are documented for Team and Pro plans and above. Scope organization secrets to selected repositories rather than all. [Managing environments](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment), [using secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions).

OpenID Connect replaces stored cloud keys with a short-lived token whose subject names the repository, environment, and branch. The protection lives in the cloud provider's trust condition; a policy that trusts any repository in the organization gives that away. [OIDC hardening](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect).

GitHub-hosted runners are new virtual machines; a self-hosted runner persists, so a fork pull request that reaches it can leave something behind. GitHub recommends self-hosted runners only for private repositories, in runner groups limited to named repositories, and ephemeral where possible. If the firm has none, record that as scoped evidence rather than skipping the control. [Runner groups](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/managing-access-to-self-hosted-runners-using-groups), [GitHub-hosted runners](https://docs.github.com/en/actions/using-github-hosted-runners/using-github-hosted-runners/about-github-hosted-runners).

## Integrations and AI features: controls 17–18

OAuth app access restrictions are enabled by default for new organizations; enabling them later revokes existing OAuth authorizations and SSH keys, so plan the reauthorization. GitHub documents GitHub Apps as preferred over OAuth apps because they use fine-grained permissions and short-lived tokens and can act without a user, which makes them the better identity for an automation or agent. Review installed apps, their permissions, and repository access on a schedule. [OAuth restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions), [enabling restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/enabling-oauth-app-access-restrictions-for-your-organization), [reviewing GitHub Apps](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/reviewing-github-apps-installed-in-your-organization), [GitHub Apps and OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps).

Copilot policies at the organization level require Copilot Business or Copilot Enterprise and cover features, third-party coding agents, MCP servers, and preview features; enterprise settings override them. The cloud agent (the current name for the coding agent) works in an ephemeral Actions environment and can be limited to selected repositories, so the Actions, ruleset, and environment controls above still govern what its pull requests can do. Content exclusion keeps confidential paths out of suggestions, with the documented limit that agent mode in IDE chat does not honor it. [Copilot policies](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/manage-policies), [adding cloud agent](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/add-copilot-cloud-agent), [about cloud agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent), [content exclusion](https://docs.github.com/en/copilot/how-tos/configure-content-exclusion/exclude-content-from-copilot), [managing access](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/manage-access).

An agent that opens pull requests is a tool with write authority. The library's [agent and MCP controls](../../cyber-risk/ai/agent-and-mcp-controls.md) describe how to record authority at each boundary, and the [agent security lab](../../labs/agent-security/README.md) shows how to test that a scope change or interrupted tool call is handled by deterministic controls rather than by trusting the model. Neither replaces the platform controls here; together they explain why GH-08, GH-13, GH-14, and GH-18 matter more once an agent holds a token.

## Monitoring and continuity: controls 19–20

The organization audit log holds 180 days and is readable by owners only. API access and audit log streaming to a storage or SIEM destination are documented for Enterprise Cloud. A Team organization that needs longer retention should schedule an export and prove it can retrieve a synthetic event. [Organization audit log](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization), [audit log streaming](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/streaming-the-audit-log-for-your-enterprise).

A mirror clone backs up Git data only; issues, pull requests, wikis, LFS objects, and organization settings need separate exports, and a migration archive does not include everything either. Measure a restore rather than trusting a job that succeeded. Pair the backup with a member export and an ownership transfer runbook, remembering that removing a departing owner does not update billing details. [Backing up a repository](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository), [exporting member information](https://docs.github.com/en/organizations/managing-membership-in-your-organization/exporting-member-information-for-your-organization), [transferring ownership](https://docs.github.com/en/organizations/managing-organization-settings/transferring-organization-ownership).

## Risk scenarios

The [risk assessment template](risk-assessment.csv) lists twelve generic scenarios for this platform, from a leaked organization-wide token to an agent merging unreviewed changes. Each row names the threat source, affected assets, and the control ids in `related_controls` that would reduce it. Ratings use the 1 to 3 likelihood and impact scale and bands from the library's [risk assessment and treatment report](../../documentation/cyber-risk/risk-assessment-and-treatment.md): 1 to 2 Low, 3 to 4 Moderate, 6 High, 9 Critical. Inherent ratings describe the scenario before controls; residual ratings assume every related control operates with fresh evidence.

The two files work together. A residual rating in the template only holds when the assessment shows each related control as aligned. If one is a gap or unknown, treat the inherent rating as current and record that in the private register. Every row is `Proposed`, with `Unassigned` and `Pending` placeholders for dates, evidence, and acceptance authority; no scenario describes a real organization, repository, or incident. The columns extend the [sanitized register schema](../../library/templates/risk-register.csv) with threat source, assets, related controls, and computed rating text.

## The first review session

Run the [fictional example](observed.example.json) with the [local assessment tool](../README.md) at `--as-of 2026-09-20`; it produces seven aligned assertions, three gaps, nine unknowns, and one scoped non-applicable control, including a stale observation, missing evidence, two unsupported native features, an approved exception that still shows as a gap, and a runner control excluded because no self-hosted runners exist in the fictional inventory.

For a real review, copy the worksheet outside the repository and choose five priority questions: who administers the organization if an owner leaves, which tokens and apps can write to production repositories, whether an agent can merge without a person, where a committed secret would be caught, and whether a critical repository can be restored with its history. Record uncertainty as unknown rather than guessing. Then use the [staged rollout plan](../rollout-and-exceptions.md) to turn each gap into a reviewed change with a pilot, a stop condition, and a rollback.
