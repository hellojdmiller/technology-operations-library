# Google Cloud: a baseline for technology operations

I would start with the blast radius. A small firm on Google Cloud usually has one or two people who hold Owner on everything, a handful of projects created by whoever needed one, a few service account keys nobody remembers downloading, and logs that live only as long as the default bucket keeps them. The organization node, the IAM bindings, and the log trail decide whether a single mistake stays inside one project. A useful baseline protects those three things first and lets the workloads themselves stay simple.

This guide is a proposed operating standard, not a certification. [One hundred and nine control assertions](desired-state.json), the [evidence worksheet](evidence-worksheet.csv), and a [risk assessment template](risk-assessment.csv) make it reviewable. They are not settings to import, a Terraform module, or a Security Command Center posture. The linked Google Cloud documentation was reviewed on **2026-09-29**; each control carries its own source and review gate. The count is high because each setting stays a separate assertion: an organization policy constraint and the resource setting it enforces are assessed separately, since one can hold while the other does not.

## Make the scope explicit

Before rating anything, record the organization resource and the Workspace or Cloud Identity account behind it, the folder and project inventory, the regions in use, the workloads and data classes per project, the recovery objectives, and which paid services are actually enabled. Keep the real details outside this repository.

Several controls depend on tiers or services that cost money. Security Command Center tier decides which detectors and services exist: most detectors cited in the evidence steps are Premium tier, Event Threat Detection needs Premium or Enterprise, and non-basic role recommendations and policy insights also need Premium or Enterprise, while basic-role recommendations are free. Two changes matter for evidence. Security Health Analytics is not available on new Security Command Center activations, which use Compliance Manager instead, so a detector name in an evidence step applies only where Security Health Analytics still runs. The Enterprise tier shuts down May 21, 2027 per the [service tiers page](https://docs.cloud.google.com/security-command-center/docs/service-tiers). Logging also bills: the [Google Cloud Observability pricing page](https://cloud.google.com/products/observability/pricing) lists log storage at $0.50/GiB with the first 50 GiB per project per month free, retention at $0.01/GiB per month beyond 30 days, and vended network logs at $0.25/GiB, while the _Required bucket keeps 400 days with no storage or retention charge. Cloud KMS keys, Backup and DR, and snapshot storage bill as well. Recording "not enabled" is a budget decision to make visible, not a reason to mark a risk as absent.

Organizations created on or after May 3, 2024 receive the Google Cloud security baseline, which enforces seven constraints at creation. The [baseline constraints page](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints) lists iam.managed.disableServiceAccountKeyCreation, iam.disableServiceAccountKeyUpload, iam.automaticIamGrantsForDefaultServiceAccounts, iam.allowedPolicyMemberDomains, essentialcontacts.managed.allowedContactDomains, compute.managed.restrictProtocolForwardingCreationForTypes, and storage.uniformBucketLevelAccess. The constraint reference and IAM pages use the legacy names for two of them (iam.disableServiceAccountKeyCreation and essentialcontacts.allowedContactDomains), so the controls name both forms. Some organizations created February to April 2024 may also have them. An older organization has none of these by default, and the review must check each one.

Two naming changes affect IAM evidence. The roles overview now names Admin, Writer, and Reader (Preview) as the basic roles, with Owner, Editor, and Viewer as legacy basic roles; the basic-role controls cover both sets. Billing Account User is documented as having very restricted permissions that can be granted broadly, so no control restricts it.

Identity itself lives in the [Google Workspace baseline](../google-workspace/README.md): dedicated least-privilege administrators ([GWS-01](../google-workspace/desired-state.json)), phishing-resistant admin sign-in ([GWS-02](../google-workspace/desired-state.json)), independent administrator recovery ([GWS-03](../google-workspace/desired-state.json)), workforce 2-step verification ([GWS-04](../google-workspace/desired-state.json)), controlled external collaboration ([GWS-05](../google-workspace/desired-state.json)), and guest review ([GWS-06](../google-workspace/desired-state.json)). Google Cloud users sign in with those Workspace or Cloud Identity accounts, and Workspace or Cloud Identity super admins assign the Organization Administrator role, so those controls are the first line of defence for this baseline too. I do not repeat them here; a Google Cloud review that finds a gap there records it against the Workspace control.

The [local assessment tool](../README.md) compares reviewer assertions recorded in a private copy of the worksheet. It does not sign in to an organization, call a Google Cloud API, read a finding, or open an evidence reference. An `aligned` result means a reviewer said the assertion held for the whole declared scope with fresh evidence; it is not an independent check of the organization.

Use three example populations when designing a pilot: a platform administrator, a developer or operator who owns one project, and a finance or operations user who only reads billing reports. Add one external CI system or integration that authenticates programmatically. The purpose is to expose a business dependency before a guardrail does.

## Organization and project structure: controls GCP-01 to GCP-12

The organization resource is the parent of every folder and project, and it is the only place an organization policy or an organization-wide IAM binding can live. Projects created outside it, or billed to a personal card, sit outside every guardrail below. New organizations also grant Project Creator and Billing Account Creator to the whole domain, so removing those grants is the first structural change. [Resource hierarchy](https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy) and [organization setup](https://docs.cloud.google.com/resource-manager/docs/creating-managing-organization).

- **GCP-01 Organization resource adopted.** Without an organization node there is no place to apply organization policies or recover projects owned by departed staff. See [Set up a Google Cloud organization resource](https://docs.cloud.google.com/resource-manager/docs/creating-managing-organization).
- **GCP-02 No projects outside the organization.** Projects outside the organization escape every org policy and cannot be recovered by the Organization Administrator when their creator leaves. See [Set up a Google Cloud organization resource](https://docs.cloud.google.com/resource-manager/docs/creating-managing-organization).
- **GCP-03 Organization Administrator roster.** At a firm of ten to fifty people one or two accounts can control every project, so the roster must be deliberate and small. See [Super administrator account best practices](https://docs.cloud.google.com/resource-manager/docs/super-admin-best-practices).
- **GCP-04 Default Project Creator grant removed.** Uncontrolled project creation produces unowned projects that fall outside review. See [Managing default organization roles](https://docs.cloud.google.com/resource-manager/docs/default-access-control).
- **GCP-05 Default Billing Account Creator grant removed.** Stray billing accounts create untracked spend and untracked projects. See [Managing default organization roles](https://docs.cloud.google.com/resource-manager/docs/default-access-control).
- **GCP-06 Project labels for owner, environment, cost centre.** Labels let one person answer who owns a project and who pays for it without asking around. See [Overview](https://docs.cloud.google.com/resource-manager/docs/labels-overview).
- **GCP-07 Named accountable owners per project.** When the creator leaves, a project owned only by that person becomes orphaned. See [About resource hierarchy](https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy).
- **GCP-08 Billing account owned by the organization.** A billing account outside the organization cannot be recovered by the Organization Administrator if its owner leaves. See [Guide to Cloud Billing Resource Organization and Access Management](https://docs.cloud.google.com/billing/docs/onboarding-checklist).
- **GCP-09 Billing Account Administrator roster.** Billing administrators can link and unlink projects and change payment details, which can stop production. See [Cloud Billing access control and permissions](https://docs.cloud.google.com/billing/docs/how-to/billing-access).
- **GCP-10 Essential Contacts: security category.** Google sends attack, vulnerability and data incident notices here; a small firm cannot afford for them to land in a leaver's inbox. See [Essential Contacts overview](https://docs.cloud.google.com/resource-manager/docs/managing-notification-contacts).
- **GCP-11 Essential Contacts: technical category.** Technical notices about service changes affect the few people who run the firm's cloud estate. See [Essential Contacts overview](https://docs.cloud.google.com/resource-manager/docs/managing-notification-contacts).
- **GCP-12 Essential Contacts: billing category.** Missed billing notices can lead to suspension of production projects. See [Essential Contacts overview](https://docs.cloud.google.com/resource-manager/docs/managing-notification-contacts).

## IAM controls: controls GCP-13 to GCP-27

Grant roles to Workspace groups, keep basic roles out of production and off the organization and folders, and treat service accounts as the main credential risk. The strongest service account control is having no user-managed keys at all: people impersonate, external CI federates, and the key constraints in the next section stop new keys appearing. [IAM roles overview](https://docs.cloud.google.com/iam/docs/roles-overview) and [service account best practices](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts).

- **GCP-13 No basic roles in production.** One compromised account with a basic role can read or change almost everything in the project. See [Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview).
- **GCP-14 Owner role limited to approved roster.** Owner is effectively full control of the project, including granting access to others. See [Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely).
- **GCP-15 No basic roles on organization or folders.** A single inherited grant at the top reaches every project the firm owns. See [Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely).
- **GCP-16 Only organization identities in IAM.** Personal accounts sit outside the firm's 2SV, offboarding and audit controls. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-17 Roles granted to groups.** Joiner and leaver changes become one group edit instead of hunting through every project. See [Use IAM securely](https://docs.cloud.google.com/iam/docs/using-iam-securely).
- **GCP-18 Predefined roles preferred; custom roles controlled.** A small team lacks time to maintain custom roles, and a mis-scoped custom role editor can grant themselves anything. See [Roles overview](https://docs.cloud.google.com/iam/docs/roles-overview).
- **GCP-19 No admin roles on user-managed service accounts.** A leaked workload credential with admin rights becomes a full account takeover. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-20 Service Account User and Token Creator not at project level.** It closes the easiest privilege-escalation path in a small project. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-21 No user-managed service account keys.** A downloaded key file is a long-lived password that works from anywhere. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-22 Unused service accounts disabled.** Dormant service accounts are unmonitored credentials an attacker can reuse. See [Find unused service accounts](https://docs.cloud.google.com/policy-intelligence/docs/service-account-insights).
- **GCP-23 Workload Identity Federation for external CI.** It removes the long-lived key that most small-firm CI pipelines otherwise store as a secret. See [Configure Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines).
- **GCP-24 Impersonation instead of keys for people.** Impersonation leaves both identities in the audit log and the credential expires within hours. See [Service account impersonation](https://docs.cloud.google.com/iam/docs/service-account-impersonation).
- **GCP-25 Role recommendations reviewed.** It shows which grants nobody actually uses without the team having to audit logs by hand. See [Overview of role recommendations](https://docs.cloud.google.com/policy-intelligence/docs/role-recommendations-overview).
- **GCP-26 No API keys unless required.** API keys are bearer credentials that are easy to leak into code or URLs. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-27 API keys restricted to specific APIs.** A restricted key limits the damage if it leaks. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).

## Resource recommendations: controls GCP-28 to GCP-109

This section pairs organization policies with the resource settings they enforce. Where both exist, the CIS reference sits only on the resource control and the constraint control says which control it enforces.

### Organization policies: controls GCP-28 to GCP-43

Constraints are inherited down the hierarchy, and a project can carry an override only where the policy allows it. Test a change in dry-run mode before enforcing it, and record each exception project by name. [Organization policy overview](https://docs.cloud.google.com/organization-policy/overview).

- **GCP-28 Disable service account key creation.** It makes the no-keys rule impossible to break by accident. See [Manage Google Cloud security baseline constraints](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints).
- **GCP-29 Disable service account key upload.** It closes the second route to a long-lived service account credential. See [Manage Google Cloud security baseline constraints](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints).
- **GCP-30 Domain-restricted sharing.** It stops anyone granting project access to a personal or partner account by mistake. See [Restrict identities with domain-restricted sharing](https://docs.cloud.google.com/organization-policy/restrict-domains).
- **GCP-31 No automatic Editor grant to default service accounts.** It removes an Editor grant that most small firms never notice exists. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-32 Prevent basic roles for default service accounts.** It stops a hurried fix from re-granting Editor to the service account attached to every VM. See [Restrict IAM service account usage](https://docs.cloud.google.com/organization-policy/restrict-service-accounts).
- **GCP-33 Exposed keys disabled automatically.** A key pushed to a public repository is disabled before someone uses it. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-34 Uniform bucket-level access required.** Access is then governed only by IAM, which is what this baseline reviews. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-35 Public access prevention enforced.** Public buckets are the most common way firm documents leak. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-36 Restrict external IPs on VMs.** Few small-firm VMs need to be reachable directly from the internet. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-37 Skip default network creation.** The default network comes with broad firewall rules nobody chose. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-38 Require OS Login.** SSH access then follows the same group-based IAM and offboarding as everything else. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-39 Disable VM serial port access.** The interactive serial console bypasses network controls. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-40 Restrict VM IP forwarding.** IP forwarding lets a compromised VM route traffic it should not. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-41 Restrict public IP on Cloud SQL.** Databases hold the firm's most sensitive records and rarely need internet addresses. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-42 Restrict Cloud SQL authorized networks.** Authorized networks are a common way a database ends up open to 0.0.0.0/0. See [Organization policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints).
- **GCP-43 Dry-run before enforcing.** A small team cannot afford an outage caused by a policy that blocks a production deploy. See [Test organization policies](https://docs.cloud.google.com/organization-policy/test-policies).

### Logging and alerting: controls GCP-44 to GCP-58

Admin Activity logs are always written, but Data Access logs are off by default for most services, and the _Default bucket keeps logs for 30 days unless someone changes it. Route logs to an organization sink in a restricted project, lock the retention there, and send alerts to channels that a person actually watches. [Cloud Audit Logs](https://docs.cloud.google.com/logging/docs/audit) and [aggregated sinks](https://docs.cloud.google.com/logging/docs/export/aggregated_sinks).

- **GCP-44 Admin Activity audit logs retained.** This is the record of who changed what in the cloud estate, and it costs nothing. See [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit).
- **GCP-45 Data Access audit logs on for all services.** Without these logs there is no record of who read a sensitive bucket or dataset, which is usually the first question after a suspected leak. See [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit).
- **GCP-46 _Default bucket retention set deliberately.** Thirty days is often too short to investigate an incident discovered weeks later, and a written choice avoids surprise gaps. See [Configure log buckets](https://docs.cloud.google.com/logging/docs/buckets).
- **GCP-47 Organization-level aggregated log sink.** One place holds the audit trail for every project, and it survives if a project is deleted or compromised. See [Aggregate and store your organization's logs](https://docs.cloud.google.com/logging/docs/central-log-storage).
- **GCP-48 Locked retention on the log destination.** An attacker or a mistaken admin with owner access cannot quietly delete the audit trail. See [Configure log buckets](https://docs.cloud.google.com/logging/docs/buckets).
- **GCP-49 Log storage in a restricted logging project.** Separating the logs from the systems they record means one compromised workload project does not expose or erase the evidence. See [Aggregate and store your organization's logs](https://docs.cloud.google.com/logging/docs/central-log-storage).
- **GCP-50 Alert on project ownership changes.** Owner grants are the quickest route to full control of a project and should never go unnoticed. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-51 Alert on audit configuration changes.** Turning off logging is a common step before misuse; an alert catches it. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-52 Alert on custom role changes.** A quietly widened custom role grants new permissions to everyone who holds it. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-53 Alert on VPC firewall rule changes.** A single opened firewall rule can expose a VM to the internet within minutes. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-54 Alert on VPC route changes.** Route changes can redirect traffic through an unintended path without any visible outage. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-55 Alert on VPC network changes.** New networks or peerings can bypass the controls on the existing ones. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-56 Alert on Cloud Storage IAM changes.** A bucket IAM change is how deal or fund data becomes public or shared outside the firm. See [Log-based metrics overview](https://docs.cloud.google.com/logging/docs/logs-based-metrics).
- **GCP-57 Cloud DNS logging on VPC networks.** DNS queries show which outside domains a compromised VM talked to, often the fastest lead in an investigation. See [Use logging and monitoring](https://docs.cloud.google.com/dns/docs/monitoring).
- **GCP-58 Notification channels owned and redundant.** An alert that goes to a departed employee or a muted inbox is the same as no alert. See [Create and manage notification channels](https://docs.cloud.google.com/monitoring/support/notification-options).

### Security Command Center: controls GCP-59 to GCP-64

Record the tier first, because it decides which detectors and services exist. Security Health Analytics is not available on new activations, where Compliance Manager is the scanner, and the Enterprise tier shuts down May 21, 2027. A finding with no owner is not a control.

- **GCP-59 Security Command Center tier recorded.** Knowing the tier tells the firm which checks are automated and which have to be done by hand. See [Security Command Center service tiers](https://docs.cloud.google.com/security-command-center/docs/service-tiers).
- **GCP-60 Security Command Center at organization level.** New projects created by anyone in the firm are covered automatically. See [Overview of activating Security Command Center](https://docs.cloud.google.com/security-command-center/docs/activate-scc-overview).
- **GCP-61 Findings routed to an owned queue.** Nobody at a small firm watches the console daily; findings must come to them. See [Enable finding notifications for Pub/Sub](https://docs.cloud.google.com/security-command-center/docs/how-to-notifications).
- **GCP-62 High and critical findings triaged.** A short, owned list is manageable for a part-time admin; an unread console is not. See [Finding severities](https://docs.cloud.google.com/security-command-center/docs/finding-severity-classifications).
- **GCP-63 Event Threat Detection enabled.** It watches the logs for signs of compromise such as malware or crypto mining that a small team would not spot by hand. See [Overview of Event Threat Detection](https://docs.cloud.google.com/security-command-center/docs/concepts-event-threat-detection-overview).
- **GCP-64 Misconfiguration scanning running.** Automated scanning is what turns this baseline into something checked continuously rather than once a year. See [Overview of Security Health Analytics](https://docs.cloud.google.com/security-command-center/docs/concepts-security-health-analytics).

### Network: controls GCP-65 to GCP-76

The default network is created in every new project with a subnet in each region and pre-populated firewall rules, so remove it and build networks deliberately. Administrative ports should never accept traffic from 0.0.0.0/0; IAP TCP forwarding gives the same access through IAM. Flow logs and firewall rules logging give an investigation something to read, and they bill as vended network logs. VPC Service Controls is the heavier option for projects that hold sensitive data; run a perimeter in dry-run mode before enforcing it. [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls) and [VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview).

- **GCP-65 Default network removed.** The default network ships with SSH and RDP open to the internet, which is the most common way a test VM gets compromised. See [VPC networks](https://docs.cloud.google.com/vpc/docs/vpc).
- **GCP-66 No SSH open to the internet.** Internet-facing SSH is scanned constantly and is a leading cause of VM compromise. See [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls).
- **GCP-67 No RDP open to the internet.** Exposed RDP is a common ransomware entry point. See [VPC firewall rules](https://docs.cloud.google.com/firewall/docs/firewalls).
- **GCP-68 Admin access through IAP TCP forwarding.** Admins reach VMs without any port open to the internet, and every session is tied to a Google identity with 2SV (see GWS-04). See [Use IAP for TCP forwarding](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding).
- **GCP-69 VPC Flow Logs on every subnet.** Flow logs show which hosts a compromised VM connected to, which is hard to reconstruct any other way. See [VPC Flow Logs](https://docs.cloud.google.com/vpc/docs/flow-logs).
- **GCP-70 Firewall rules logging on key rules.** Shows whether an internet-facing rule is actually being hit, and by whom. See [VPC firewall rules logging overview](https://docs.cloud.google.com/firewall/docs/vpc-firewall-rules-logging-overview).
- **GCP-71 Private Google Access on internal subnets.** Lets internal-only VMs use Cloud Storage and other Google APIs without giving them public IP addresses. See [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access).
- **GCP-72 Cloud NAT for outbound internet.** VMs can fetch updates without being reachable from the internet. See [Cloud NAT overview](https://docs.cloud.google.com/nat/docs/overview).
- **GCP-73 Hierarchical firewall policy at org or folder.** One policy set by the admin cannot be loosened by a project owner editing local firewall rules. See [Firewall policies and rules](https://docs.cloud.google.com/firewall/docs/firewall-policies-overview).
- **GCP-74 VPC Service Controls perimeter for sensitive data.** Stops stolen credentials from copying data out to a project or network outside the firm. See [Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview).
- **GCP-75 Perimeter changes tested in dry-run mode.** Avoids locking the firm out of its own data or breaking a reporting job on the day of enforcement. See [Dry run mode for service perimeters](https://docs.cloud.google.com/vpc-service-controls/docs/dry-run-mode).
- **GCP-76 Perimeter access through defined access levels.** Exceptions are where perimeters leak; naming and owning each one keeps them few. See [Access Context Manager Overview](https://docs.cloud.google.com/access-context-manager/docs/overview).

### Cloud Storage: controls GCP-77 to GCP-81

Public access prevention and uniform bucket-level access close the two usual paths to a public bucket; soft delete and versioning give a recovery window after a mistaken or malicious deletion. [Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention).

- **GCP-77 No public principals on buckets.** A single public grant can expose deal documents or LP data to anyone on the internet who knows the object URL. See [Make data public](https://docs.cloud.google.com/storage/docs/access-control/making-data-public).
- **GCP-78 Public access prevention on every bucket.** It turns an accidental public grant into a failed request instead of a data exposure. See [Public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention).
- **GCP-79 Uniform bucket-level access on.** One IAM policy per bucket is far easier for a small team to review than per-object ACLs. See [Uniform bucket-level access](https://docs.cloud.google.com/storage/docs/uniform-bucket-level-access).
- **GCP-80 Soft delete retention kept.** It gives a week to recover files deleted by mistake or by a compromised account. See [Soft delete overview](https://docs.cloud.google.com/storage/docs/soft-delete).
- **GCP-81 Object Versioning on critical buckets.** It protects against overwrites of key files, which soft delete alone does not keep. See [Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning).

### KMS and secrets: controls GCP-82 to GCP-87

Keys protect backups and logs as well as live data, so treat key changes as recovery changes. Application secrets belong in Secret Manager with access granted per secret, not in environment variables.

- **GCP-82 KMS key rotation within 90 days.** Regular rotation limits how much data one compromised key version exposes. See [Key rotation](https://docs.cloud.google.com/kms/docs/key-rotation).
- **GCP-83 No public access to KMS keys.** A publicly usable key lets anyone decrypt or sign with it. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).
- **GCP-84 Separate KMS admins from key users.** The person who can destroy a key should not also be the one quietly decrypting data with it. See [Separation of duties](https://docs.cloud.google.com/kms/docs/separation-of-duties).
- **GCP-85 Key destruction delay kept.** A mistaken or malicious key deletion can be reversed within the window instead of losing the data it protects. See [Destroy and restore key versions](https://docs.cloud.google.com/kms/docs/destroy-restore).
- **GCP-86 Secrets in Secret Manager, not env vars.** Environment variables leak through debug endpoints and logs, and anyone who can view the service config can read them. See [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices).
- **GCP-87 Secret access granted per secret.** Least privilege at the secret level stops one compromised service from reading every other credential. See [Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices).

### Compute Engine: controls GCP-88 to GCP-96

Default service accounts, project-wide SSH keys, serial ports, and external IPs are the common ways a single VM becomes a path into the project. If the firm runs no VMs, record that as a scoped not-applicable with inventory evidence and a trigger for reassessment.

- **GCP-88 VMs do not use the default service account.** A compromised VM running as a broadly privileged default account can change the whole project. See [Service accounts](https://docs.cloud.google.com/compute/docs/access/service-accounts).
- **GCP-89 Default service account without full API scope.** Full scope on the default account gives any code on the VM the account's full project permissions. See [Service accounts](https://docs.cloud.google.com/compute/docs/access/service-accounts).
- **GCP-90 Project-wide SSH keys blocked.** One key in project metadata opens every VM in the project, including to people who have left. See [Restrict SSH keys from VMs](https://docs.cloud.google.com/compute/docs/connect/restrict-ssh-keys).
- **GCP-91 OS Login enabled.** SSH access follows IAM, so removing a person's Google account or role removes their server access. See [About OS Login](https://docs.cloud.google.com/compute/docs/oslogin).
- **GCP-92 OS Login 2-step verification.** A stolen SSH key or session alone is not enough to reach a server. See [Set up OS Login](https://docs.cloud.google.com/compute/docs/oslogin/set-up-oslogin).
- **GCP-93 Serial port access disabled.** An enabled serial console can be reached from any IP address by anyone with the right key and names. See [Troubleshooting using the serial console](https://docs.cloud.google.com/compute/docs/troubleshooting/troubleshooting-using-serial-console).
- **GCP-94 IP forwarding off.** An unexpected router VM can be used to move traffic around network controls. See [Use routes](https://docs.cloud.google.com/vpc/docs/using-routes).
- **GCP-95 Shielded VM enabled.** It helps detect tampering with the boot sequence of servers the firm runs. See [Shielded VM overview](https://docs.cloud.google.com/compute/shielded-vm/docs/shielded-vm).
- **GCP-96 No external IP on VMs.** A VM without a public address cannot be scanned or attacked directly from the internet. See [IP addresses](https://docs.cloud.google.com/compute/docs/ip-addresses).

### Cloud SQL and BigQuery: controls GCP-97 to GCP-101

Databases should have no public IP, no open authorized networks, and encrypted connections; BigQuery datasets should never grant access to allUsers or allAuthenticatedUsers. If the firm runs no Cloud SQL, record that as a scoped not-applicable.

- **GCP-97 Cloud SQL without public IP.** A database without a public address is not exposed to internet scanning or password guessing. See [Choose how to connect to Cloud SQL](https://docs.cloud.google.com/sql/docs/postgres/connection-options).
- **GCP-98 No open authorized networks on Cloud SQL.** An open range lets anyone on the internet try to log in to the database. See [Authorize with authorized networks](https://docs.cloud.google.com/sql/docs/postgres/authorize-networks).
- **GCP-99 Cloud SQL requires SSL/TLS.** Database traffic carrying portfolio or fund data should not cross networks in clear text. See [Configure SSL/TLS certificates](https://docs.cloud.google.com/sql/docs/postgres/configure-ssl-instance).
- **GCP-100 MySQL root user has a password.** The passwordless root account is a common target and gives near-unlimited control of the database. See [About MySQL users](https://docs.cloud.google.com/sql/docs/mysql/users).
- **GCP-101 BigQuery datasets not public.** A public dataset exposes every table in it to anyone with a Google account or no account at all. See [Vulnerability findings](https://docs.cloud.google.com/security-command-center/docs/concepts-vulnerabilities-findings).

### Backup and recovery: controls GCP-102 to GCP-107

A backup job that succeeds settles nothing about recovery. Keep automated backups and deletion protection on databases, attach snapshot schedules to disks, place liens on critical projects, and record a restore.

- **GCP-102 Cloud SQL automated backups on.** Without backups, one bad migration or deletion can lose the firm's application data. See [Configure point-in-time recovery (PITR)](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/configure-pitr).
- **GCP-103 Cloud SQL point-in-time recovery on.** It allows recovery to the minute before a mistaken change rather than to last night's backup. See [Configure point-in-time recovery (PITR)](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/configure-pitr).
- **GCP-104 Cloud SQL deletion protection on.** It stops a single mistaken command from removing the firm's database. See [Prevent deletion of an instance](https://docs.cloud.google.com/sql/docs/postgres/deletion-protection).
- **GCP-105 Snapshot schedules as the simpler alternative.** Regular snapshots are a low-effort way to recover a VM disk after a failure or mistake. See [Create schedules for disk snapshots](https://docs.cloud.google.com/compute/docs/disks/scheduled-snapshots).
- **GCP-106 Restore test recorded.** A backup that has never been restored is an untested assumption. See [Perform point-in-time recovery (PITR)](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/pitr).
- **GCP-107 Project liens on critical projects.** It prevents a single mistaken or malicious action from deleting everything in a project. See [Protect projects with liens](https://docs.cloud.google.com/resource-manager/docs/project-liens).

### Billing and labels: controls GCP-108 to GCP-109

Budgets and cost anomalies are cheap abuse signals. Budget alerts notify but do not cap spend, so treat an unexpected alert as a security triage item, not only a finance one. [Budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets).

- **GCP-108 Budgets with threshold alerts.** A leaked key or runaway job can run up a large bill before anyone looks at the invoice. See [Create, edit, or delete budgets and budget alerts](https://docs.cloud.google.com/billing/docs/how-to/budgets).
- **GCP-109 Cost anomalies reviewed.** It flags an unusual spike without the team having to set thresholds per project. See [View and manage cost anomalies](https://docs.cloud.google.com/billing/docs/how-to/manage-anomalies).

## Risk scenarios

The [risk assessment template](risk-assessment.csv) lists twelve generic scenarios for this platform: a leaked service account key, a public bucket holding diligence material, a departed person or personal account still holding a role, a deleted project or backup, a Security Command Center finding nobody owns, an internet-exposed VM, a default service account with broad access, disabled or deleted audit logs, an IAM or firewall change nobody notices, a secret kept in configuration or code, runaway spend after credential compromise, and a destroyed or exposed encryption key. No row describes a real organization, project, or incident.

Each row's `related_controls` field names the control ids from [desired-state.json](desired-state.json) that would reduce it. Likelihood and impact use the library's 1 to 3 scale and bands from the [risk assessment and treatment method](../../documentation/cyber-risk/risk-assessment-and-treatment.md): 1 to 2 Low, 3 to 4 Moderate, 6 High, 9 Critical. The inherent rating describes the scenario with none of the related controls in place. The residual rating assumes every related control operates and is evidenced, which in assessment terms means each related control shows `aligned`. If any related control is a gap or unknown, the residual rating has not been earned and the inherent rating stands until evidence arrives.

Every row is `Proposed`, with `Unassigned` and `Pending` placeholders for dates, verification evidence, and acceptance authority. The columns extend the [library risk register template](../../library/templates/risk-register.csv) with threat source, affected assets, related controls, and written ratings so the register and the baseline can be read together. Replace the scenarios, agree the scoring with the sponsor, and keep the completed register in the firm's protected record.

## The first review session

Run the [fictional example](observed.example.json) with the [local assessment tool](../README.md):

```sh
node baselines/scripts/assess.mjs baselines/gcp/desired-state.json baselines/gcp/observed.example.json --as-of 2026-09-29
```

It reports 7 aligned, 3 gaps, 98 unknown, and 1 not applicable, and includes a stale observation, a missing evidence reference, an unsupported service, an approved exception that still shows as a gap, a partial scope, and a scoped not-applicable control. Every value in it is invented.

For a real review, copy the worksheet and the risk template outside the repository and choose five priority questions: who holds Owner and Organization Administrator, and whether any of them is outside the firm's domain; whether any user-managed service account key exists and who could use it; whether every project's audit logs reach a locked destination that a project owner cannot delete; whether a public bucket, open SSH port, or public database could exist without someone knowing; and whether a restore has been proved without depending on a key or an administrator who might be gone. Record uncertainty as unknown. Then use the [staged rollout plan](../rollout-and-exceptions.md) to turn evidence into specific, reversible changes.
