# Microsoft Azure: a baseline for technology operations

I would start with the blast radius. A small firm on Azure usually has one tenant, a few subscriptions that grew one project at a time, a Global Administrator who can elevate into every subscription with one toggle, and storage accounts that were opened to the internet to make a test work. The management group hierarchy, the path from Entra roles into Azure roles, and the log trail decide whether a single mistake stays inside one subscription. A useful baseline protects those three things first and lets the workloads themselves stay simple.

This guide is a proposed operating standard, not a certification. [Ninety-nine control assertions](desired-state.json), the [evidence worksheet](evidence-worksheet.csv), and a [risk assessment template](risk-assessment.csv) make it reviewable. They are not settings to import, a Bicep template, or an Azure Policy initiative. The linked Microsoft Learn documentation was reviewed on **2026-09-29**; each control carries its own source and review gate, and each review gate opens with the documented default and, where Microsoft publishes one, the CIS Azure Foundations 2.0.0 reference.

## Make the scope explicit

Before rating anything, record the Entra tenant, the management group tree, every subscription and its purpose, the approved regions, the workloads and data classes per subscription, the recovery objectives, and which paid plans are actually enabled. Keep the real details outside this repository.

Several controls depend on licences or plans that cost money. Privileged Identity Management for Azure resource roles and PIM access reviews need Microsoft Entra ID P2 or Microsoft Entra ID Governance for every user with an eligible or time-bound assignment. Defender for Servers, Storage, Key Vault, Resource Manager, App Service, Azure SQL, and Containers are paid Defender for Cloud plans; Foundational CSPM and the Microsoft cloud security benchmark are free. Azure Bastion, Azure Backup, vault soft delete retention beyond 14 days, Log Analytics ingestion and retention beyond the included period, Activity Log retention beyond 90 days, VNet flow logs beyond the free tier, private endpoints, and Microsoft Sentinel all bill. Recording "not enabled" is a budget decision to make visible, not a reason to mark a risk as absent.

Identity itself lives in the [Microsoft 365 baseline](../microsoft-365/README.md), because Azure and Microsoft 365 share one Entra tenant. MFA and authentication strength ([M365-02](../microsoft-365/desired-state.json) and [M365-03](../microsoft-365/desired-state.json)), emergency access account design ([M365-04](../microsoft-365/desired-state.json)), Entra directory role hygiene ([M365-05](../microsoft-365/desired-state.json)), guest lifecycle ([M365-10](../microsoft-365/desired-state.json)), application ownership and consent ([M365-12](../microsoft-365/desired-state.json)), Entra sign-in and audit log retention ([M365-16](../microsoft-365/desired-state.json)), and PIM for directory roles ([M365-23](../microsoft-365/desired-state.json)) are assessed there once. Repeating them here would create two answers to the same question. This baseline covers only what happens on the Azure side: Azure RBAC assignments, the elevation path from Global Administrator to root scope, the Azure management MFA policy, and the credentials workloads use against Azure.

The [local assessment tool](../README.md) compares reviewer assertions recorded in a private copy of the worksheet. It does not sign in to a tenant, call an Azure API, read a recommendation, or open an evidence reference. An `aligned` result means a reviewer said the assertion held for the whole declared scope with fresh evidence; it is not an independent check of the tenant.

Use three example populations when designing a pilot: a platform administrator, a developer or operator who owns one workload, and a finance or operations user who only reads cost reports. Add one CI pipeline or integration that authenticates as a workload identity. The purpose is to expose a business dependency before a guardrail does.

## Tenant and subscription structure: controls AZ-01 to AZ-09

Management groups are where guardrails attach once and inherit everywhere, and the root is where one assignment reaches every subscription. [Management groups](https://learn.microsoft.com/en-us/azure/governance/management-groups/overview), [protect the resource hierarchy](https://learn.microsoft.com/en-us/azure/governance/management-groups/how-to/protect-resource-hierarchy), the Cloud Adoption Framework pages on [management groups](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/resource-org-management-groups) and [subscriptions](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/resource-org-subscriptions), [elevate access](https://learn.microsoft.com/en-us/azure/role-based-access-control/elevate-access-global-admin), and [subscription policies](https://learn.microsoft.com/en-us/azure/cost-management-billing/manage/manage-azure-subscription-policy).

- **AZ-01 Intermediate root management group.** New subscriptions land in the tenant root by default, and one intermediate group gives a small firm a place to apply guardrails without touching the root.
- **AZ-02 Default management group for new subscriptions.** Pointing new subscriptions at a sandbox group means a subscription somebody creates on a Friday inherits restrictive policy rather than none.
- **AZ-03 Authorization required to create management groups.** Any user can create management groups by default, and a stray group outside the governed tree escapes its policies.
- **AZ-04 Production separated by subscription.** A subscription is the boundary for billing, policy, and role assignments, so production should not share one with experiments.
- **AZ-05 No standing access at root scope.** An assignment at root reaches every subscription at once, which for a small firm usually means everything it runs.
- **AZ-06 Elevate access toggle off when not in use.** One toggle turns any Global Administrator into User Access Administrator at root, and it stays on until someone turns it off.
- **AZ-07 Elevate access events are alerted.** Elevation is rare in a small firm, so every event is worth a human look.
- **AZ-08 Subscriptions cannot leave the directory.** A transferred subscription takes the firm's data and resources outside its tenant and its logs; Allow no users is the documented default since May 1st, 2026.
- **AZ-09 Subscriptions cannot enter the directory.** A subscription moved in from elsewhere brings resources and billing the firm did not approve.

## IAM controls: controls AZ-10 to AZ-30

Azure roles and Entra roles are separate systems, and the Azure side needs its own roster, its own PIM settings, and its own review. [Azure RBAC best practices](https://learn.microsoft.com/en-us/azure/role-based-access-control/best-practices), [Azure and Entra roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/rbac-and-directory-admin-roles), [delegating role assignments](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview), [PIM role settings for Azure resources](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-resource-roles-configure-role-settings), [ID Governance licensing](https://learn.microsoft.com/en-us/entra/id-governance/licensing-fundamentals), and the Defender for Cloud [identity recommendations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/recommendations-reference-identity-access).

- **AZ-10 More than one subscription owner.** If the only owner leaves or loses a device, nobody can administer the subscription.
- **AZ-11 At most three subscription owners.** Every extra owner is one more account whose compromise gives away the whole subscription.
- **AZ-12 Privileged roles assigned at narrow scope.** An Owner assignment on a management group reaches every child subscription, so it belongs to the platform roster only.
- **AZ-13 Role assignment rights limited and constrained.** User Access Administrator and RBAC Administrator can grant Owner to themselves unless a condition stops them.
- **AZ-14 Roles assigned to groups.** Group assignments make joiners, movers, and leavers one change instead of a hunt across subscriptions.
- **AZ-15 No permanent active Owner or User Access Administrator.** Standing privilege is exposed every hour of every day; eligible access is exposed only during a task.
- **AZ-16 PIM activation requires MFA.** Activation is the moment privilege appears, so it deserves a fresh strong sign-in.
- **AZ-17 PIM activation duration limited.** A short activation window closes the door behind the administrator.
- **AZ-18 Owner activation requires approval.** A second named person sees every Owner activation; there are no default approvers, so name two.
- **AZ-19 Recurring access review of Azure roles.** Assignments accumulate quietly, and a quarterly [PIM access review](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-create-roles-and-resource-roles-review) is where they are removed.
- **AZ-20 No custom subscription administrator roles.** [Custom roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles) are error prone and can hide Owner-equivalent rights behind an innocent name.
- **AZ-21 Blocked accounts removed from Azure roles.** Disabling a leaver's Entra account does not remove their Azure roles, and dormant assignments attract attackers.
- **AZ-22 No guest accounts with Owner on Azure.** Guests are managed by another organization's standards, so they should never own a subscription.
- **AZ-23 Service principals not given admin roles.** A deployment identity with Owner at subscription scope is a standing credential with full control.
- **AZ-24 Managed identities for Azure-hosted workloads.** [Managed identities](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview) remove the stored secret entirely, including for [App Service](https://learn.microsoft.com/en-us/azure/app-service/overview-managed-identity).
- **AZ-25 Federated credentials for external CI.** [Workload identity federation](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation) lets [GitHub Actions](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-openid-connect) deploy without a secret sitting in the CI system.
- **AZ-26 No client secrets on Azure app registrations.** Client secrets are the credential most often pasted into scripts and forgotten; see the [app registration best practices](https://learn.microsoft.com/en-us/entra/identity-platform/security-best-practices-for-app-registration).
- **AZ-27 Conditional Access requires MFA for Azure management.** A [policy on Windows Azure Service Management API](https://learn.microsoft.com/en-us/entra/identity/conditional-access/policy-old-require-mfa-azure-mgmt) covers the portal, PowerShell, and CLI in one place.
- **AZ-28 Mandatory Azure MFA not postponed.** Microsoft's [mandatory MFA](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-mandatory-multifactor-authentication) is a free floor, and a postponement quietly removes it.
- **AZ-29 User accounts not used as Azure service accounts.** A person's account running automation is hard to protect and breaks once mandatory MFA applies.
- **AZ-30 Emergency access on the Azure side.** The [emergency accounts](https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/security-emergency-access) from M365-04 must still reach Azure when federation or Conditional Access fails; holding no standing Azure role and reaching Azure only through elevation is this baseline's own design, not a Microsoft instruction.

## Resource recommendations: controls AZ-31 to AZ-99

### Policy and guardrails: AZ-31 to AZ-34

[Azure Policy](https://learn.microsoft.com/en-us/azure/governance/policy/overview) assignments inherit down the hierarchy, and a [deny effect](https://learn.microsoft.com/en-us/azure/governance/policy/concepts/effect-deny) returns 403 on create and update, so run audit first and record the switch.

- **AZ-31 Microsoft cloud security benchmark assigned.** The [MCSB](https://learn.microsoft.com/en-us/azure/defender-for-cloud/concept-regulatory-compliance-standards) gives a small team a maintained baseline instead of policy written from scratch; see [security policies](https://learn.microsoft.com/en-us/azure/defender-for-cloud/security-policy-concept).
- **AZ-32 Allowed locations policy.** The [built-in policy](https://learn.microsoft.com/en-us/azure/governance/policy/samples/built-in-policies) keeps data in the regions the firm has approved and makes a stray deployment fail loudly.
- **AZ-33 Required tags on resource groups.** An ownership tag on every resource group answers "whose is this?" during an incident; see [governing tags](https://learn.microsoft.com/en-us/azure/governance/policy/tutorials/govern-tags), the [tagging guidance](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/resource-tagging), and [tag behavior](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/tag-resources).
- **AZ-34 Policy exemptions expire and have an owner.** An [exemption](https://learn.microsoft.com/en-us/azure/governance/policy/concepts/exemption-structure) without `expiresOn` lasts forever, which turns a temporary waiver into a permanent hole.

### Defender for Cloud: AZ-35 to AZ-45

Foundational CSPM is free; the workload plans are paid and chosen per subscription. [Foundational CSPM](https://learn.microsoft.com/en-us/azure/defender-for-cloud/concept-cloud-security-posture-management) becomes opt-in for new Azure subscriptions from October 27, 2026, as the page states, so enablement belongs on the subscription creation checklist. [Defender for Cloud overview](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-cloud-introduction).

- **AZ-35 Foundational CSPM enabled on every subscription.** A subscription created after the opt-in change would otherwise produce no recommendations at all.
- **AZ-36 Secure score reviewed and recommendations owned.** A [secure score](https://learn.microsoft.com/en-us/azure/defender-for-cloud/secure-score-security-controls) nobody reads changes nothing.
- **AZ-37 Defender for Servers plan selected.** [Plan 1 or Plan 2](https://learn.microsoft.com/en-us/azure/defender-for-cloud/plan-defender-for-servers-select-plan) is the difference between endpoint detection only and the extra scanning and just-in-time features.
- **AZ-38 Defender for Storage enabled.** [Defender for Storage](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-storage-introduction) watches the accounts that hold deal and investor files.
- **AZ-39 Defender for Key Vault enabled.** [Defender for Key Vault](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-key-vault-introduction) flags unusual access to the secrets everything else depends on.
- **AZ-40 Defender for Resource Manager enabled.** [Defender for Resource Manager](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-resource-manager-introduction) watches the management plane, which is where a stolen administrator session acts.
- **AZ-41 Defender for App Service enabled where used.** [Defender for App Service](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-app-service-introduction) covers internet-facing apps, the most exposed thing a small firm runs.
- **AZ-42 Defender for Azure SQL Databases enabled where used.** [Defender for SQL](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-sql-introduction) detects injection and unusual access to the firm's records.
- **AZ-43 Defender for Containers enabled where containers are used.** [Defender for Containers](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-containers-introduction) matters only if the firm runs Kubernetes or a container registry, and then it covers images and clusters nobody else is watching.
- **AZ-44 Security contact email configured.** [Email notifications](https://learn.microsoft.com/en-us/azure/defender-for-cloud/configure-email-notifications) to a shared monitored mailbox survive one person's holiday.
- **AZ-45 Alert notification severity and owner role.** High-severity alerts reaching the subscription Owner make sure someone accountable hears first.

### Logging and alerting: AZ-46 to AZ-62

The [Activity Log](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/activity-log) keeps 90 days in the platform and nothing further without a [diagnostic setting](https://learn.microsoft.com/en-us/azure/azure-monitor/data-collection/diagnostic-settings). Activity log alerts are [stateless](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-types) and fire on each matching operation; the operation names come from the [management and governance](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/management-and-governance), networking, security, and databases permission pages ([networking](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/networking)). NSG flow logs retire on September 30, 2027, as the page states, and no longer support new creation.

- **AZ-46 Activity Log exported to Log Analytics.** Every category in one workspace (see the [event schema](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/activity-log-schema)) is the minimum for answering who changed what.
- **AZ-47 Activity Log retention beyond 90 days.** Incidents are often found months after they start, and [retention](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/data-retention-configure) past 90 days is cheap insurance.
- **AZ-48 Workspace retention set deliberately.** The 30-day table default is shorter than most investigations; the [cost page](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/cost-logs) shows what longer costs.
- **AZ-49 Key Vault AuditEvent logging.** [Key Vault logging](https://learn.microsoft.com/en-us/azure/key-vault/general/logging) is the only record of who read which secret.
- **AZ-50 Resource logs for all supporting services.** Resource logs are not collected by default, so an unlogged service is a blind spot.
- **AZ-51 VNet flow logs replace NSG flow logs.** [VNet flow logs](https://learn.microsoft.com/en-us/azure/network-watcher/vnet-flow-logs-overview) are the documented replacement for [NSG flow logs](https://learn.microsoft.com/en-us/azure/network-watcher/nsg-flow-logs-overview) and show where traffic actually went.
- **AZ-52 Alert on create policy assignment.** A new assignment can change what every resource below it is allowed to do.
- **AZ-53 Alert on delete policy assignment.** Deleting an assignment is the quietest way to remove a guardrail.
- **AZ-54 Alert on create or update NSG.** A changed NSG is how a management port ends up open to the internet.
- **AZ-55 Alert on delete NSG.** Deleting an NSG removes filtering from everything attached to it.
- **AZ-56 Alert on create or update security solution.** A changed security solution can quietly redirect or weaken protection; the operation name is on the [security permissions](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/security) page.
- **AZ-57 Alert on delete security solution.** Removing a security solution is a step an attacker takes before acting.
- **AZ-58 Alert on create or update SQL firewall rule where Azure SQL is used.** A new firewall rule is how a database ends up reachable from the internet; see the [database permissions](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/databases) page.
- **AZ-59 Alert on delete SQL firewall rule where Azure SQL is used.** A deleted rule can break the firm's own access or hide an earlier change.
- **AZ-60 Alert on role assignment write.** A new role assignment is the step an attacker takes to keep access.
- **AZ-61 Alert on role assignment delete.** Removed assignments can lock out the people who would respond.
- **AZ-62 Action groups reach a monitored channel.** An [action group](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups) that emails one person is a gap whenever that person is away.

### Key Vault: AZ-63 to AZ-69

Key Vault holds the secrets and keys that everything else depends on. [Soft delete](https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview) is on by default for new vaults, which is why it is not a separate control here; purge protection is not. [Recovery](https://learn.microsoft.com/en-us/azure/key-vault/general/key-vault-recovery) and [securing Key Vault](https://learn.microsoft.com/en-us/azure/key-vault/general/secure-key-vault).

- **AZ-63 Key Vault purge protection enabled.** Without it a compromised administrator can make deletion permanent immediately.
- **AZ-64 Key Vault uses the Azure RBAC permission model.** [RBAC](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide) puts vault access into the same review as everything else; [access policies](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-access-policy) sit outside it.
- **AZ-65 Key Vault public network access restricted.** The [firewall](https://learn.microsoft.com/en-us/azure/key-vault/general/network-security) is off by default, so a stolen token works from anywhere.
- **AZ-66 Key Vault keys have an expiration date.** An expiry forces the rotation conversation before a key has lived for years.
- **AZ-67 Key Vault secrets have an expiration date.** A secret with a date gets an owner who renews it.
- **AZ-68 Key rotation policy on Key Vault keys.** A [rotation policy](https://learn.microsoft.com/en-us/azure/key-vault/keys/how-to-configure-key-rotation) makes rotation routine instead of an emergency.
- **AZ-69 Key Vault data roles scoped to the vault.** A Secrets role at subscription scope reads every vault in it.

### Storage accounts: AZ-70 to AZ-79

Storage accounts are where a small firm's documents end up. [Blob security recommendations](https://learn.microsoft.com/en-us/azure/storage/blobs/security-recommendations).

- **AZ-70 Anonymous blob access disallowed.** [Preventing anonymous access](https://learn.microsoft.com/en-us/azure/storage/blobs/anonymous-read-access-prevent) at the account level means no container can be made public by mistake.
- **AZ-71 Shared Key authorization disallowed.** [Account keys](https://learn.microsoft.com/en-us/azure/storage/common/shared-key-authorization-prevent) bypass Entra identity, Conditional Access, and per-user audit.
- **AZ-72 SAS expiration policy where Shared Key remains.** A [SAS expiration policy](https://learn.microsoft.com/en-us/azure/storage/common/sas-expiration-policy) caps how long a shared link can live.
- **AZ-73 Secure transfer required on storage accounts.** [Secure transfer](https://learn.microsoft.com/en-us/azure/storage/common/storage-require-secure-transfer) rejects plain HTTP.
- **AZ-74 Minimum TLS 1.2 on storage accounts.** Accounts created by CLI or template may have no [minimum TLS version](https://learn.microsoft.com/en-us/azure/storage/common/transport-layer-security-configure-minimum-version) set.
- **AZ-75 Storage firewall default action Deny.** The [storage firewall](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security) allows every network by default, so a stolen key works from anywhere.
- **AZ-76 Blob soft delete enabled with retention.** [Blob soft delete](https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-overview) turns an accidental deletion into a [restore](https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-enable).
- **AZ-77 Container soft delete enabled with retention.** [Container soft delete](https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-container-overview) covers the deletion of a whole folder of files.
- **AZ-78 Blob versioning enabled.** [Versioning](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview) recovers a file that was overwritten or encrypted, not only deleted.
- **AZ-79 Cross-tenant object replication disallowed.** [Cross-tenant replication](https://learn.microsoft.com/en-us/azure/storage/blobs/object-replication-prevent-cross-tenant-policies) can copy data to a tenant the firm does not control.

### Network: AZ-80 to AZ-84

- **AZ-80 No NSG rule allows RDP from the internet.** Open management ports are scanned within minutes; see the [network best practices](https://learn.microsoft.com/en-us/azure/security/fundamentals/network-best-practices) and [networking recommendations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/recommendations-reference-networking).
- **AZ-81 No NSG rule allows SSH from the internet.** The same exposure applies to Linux VMs.
- **AZ-82 Just-in-time access for VM management ports.** [Just-in-time access](https://learn.microsoft.com/en-us/azure/defender-for-cloud/just-in-time-access-overview) opens a port only for an approved source and time window; it needs the paid Defender for Servers Plan 2.
- **AZ-83 Azure Bastion for VM remote access.** [Azure Bastion](https://learn.microsoft.com/en-us/azure/bastion/bastion-overview) gives administrators a path in without a public IP on the VM.
- **AZ-84 Azure SQL firewall closed to the internet.** [Allowing Azure services](https://learn.microsoft.com/en-us/azure/azure-sql/database/firewall-configure?view=azuresql) admits other customers' resources, and a [private endpoint](https://learn.microsoft.com/en-us/azure/azure-sql/database/private-endpoint-overview?view=azuresql) does not block public routing by itself.

### Compute and databases: AZ-85 to AZ-91

- **AZ-85 Microsoft Entra-only authentication for Azure SQL.** [Entra-only authentication](https://learn.microsoft.com/en-us/azure/azure-sql/database/authentication-azure-ad-only-authentication?view=azuresql) removes SQL passwords that have no MFA or Conditional Access.
- **AZ-86 Azure SQL auditing enabled.** [Auditing](https://learn.microsoft.com/en-us/azure/azure-sql/database/auditing-overview?view=azuresql) is the record of who queried the firm's data.
- **AZ-87 Azure SQL audit retention over 90 days.** [Audit retention](https://learn.microsoft.com/en-us/azure/azure-sql/database/auditing-setup?view=azuresql) should outlast the time it takes to notice an incident.
- **AZ-88 Transparent data encryption on Azure SQL.** [TDE](https://learn.microsoft.com/en-us/azure/azure-sql/database/transparent-data-encryption-tde-overview?view=azuresql) is on by default and should stay on.
- **AZ-89 App Service HTTPS only.** HTTPS Only is not on by default, per [App Service security](https://learn.microsoft.com/en-us/azure/app-service/overview-security), so an internet-facing app can still answer over plain HTTP.
- **AZ-90 App Service FTP disabled.** Plain [FTP](https://learn.microsoft.com/en-us/azure/app-service/deploy-ftp) sends publishing credentials and content unencrypted.
- **AZ-91 App Service basic auth publishing disabled.** Username and password publishing bypasses Entra ID and MFA.

### Backup and recovery: AZ-92 to AZ-97

- **AZ-92 Delete locks on production resource groups.** A [CanNotDelete lock](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources) stops one mistaken click from removing a whole environment.
- **AZ-93 Azure Backup protects VMs.** [Azure Backup](https://learn.microsoft.com/en-us/azure/backup/backup-overview) for [VMs](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-introduction) is the recovery path when a server is lost or encrypted.
- **AZ-94 Recovery Services vault soft delete retention.** [Secure by default](https://learn.microsoft.com/en-us/azure/backup/secure-by-default) soft delete keeps deleted backups for at least 14 days.
- **AZ-95 Immutable vault enabled and locked.** A locked [immutable vault](https://learn.microsoft.com/en-us/azure/backup/backup-azure-immutable-vault-concept) stops a compromised administrator reducing retention.
- **AZ-96 Backup restore test recorded.** A successful backup job settles nothing about recovery; the restore test does, and [vault options](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault) such as Cross Region Restore can serve for drills.
- **AZ-97 Azure SQL point-in-time restore retention.** The 7-day [default](https://learn.microsoft.com/en-us/azure/azure-sql/database/automated-backups-overview?view=azuresql) may be shorter than the time it takes to notice bad data.

### Cost: AZ-98 to AZ-99

- **AZ-98 Budget with actual and forecast alerts per subscription.** A [budget](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets) is the cheapest abuse signal a small firm has, though it notifies and never stops spend.
- **AZ-99 Cost anomaly alert per subscription.** An [anomaly alert](https://learn.microsoft.com/en-us/azure/cost-management-billing/understand/analyze-unexpected-charges) catches cryptomining before the invoice does.

## Settings to disable or remove without compensating controls

Each row is a setting I would not leave on, or a state I would not leave in place, unless the named compensating control is in place and evidenced.

| Setting | Default | Why it matters | Compensating control that would allow it | Control |
|---|---|---|---|---|
| Management group creation open to all users (requireAuthorizationForGroupCreation false) | Any user, by default, can create new management groups in a tenant | Uncontrolled management groups break the single governed hierarchy. | None documented; enable the require-authorization setting. | [AZ-03](desired-state.json) |
| Standing role assignments at root scope | No one has default access to the root management group | Root-scope access controls every subscription and management group in the tenant. | A documented, time-limited exception with alerting on the assignment. | [AZ-05](desired-state.json) |
| Access management for Azure resources set to Yes | Not elevated until a Global Administrator sets the toggle to Yes | It assigns User Access Administrator at root scope (/). | Elevation only for a recorded task, then reset to No, with alerts on elevate-access log entries (AZ-07). | [AZ-06](desired-state.json) |
| Subscriptions leaving directory: Allow all users | Allow no users | Subscription owners could transfer subscriptions to another directory. | Named exempted users for a planned transfer, removed afterwards. | [AZ-08](desired-state.json) |

## Risk scenarios

The [risk assessment template](risk-assessment.csv) lists twelve generic scenarios for this platform: a leaked app registration secret, a storage account open to anonymous or all-network access, an elevated Global Administrator left at root, deleted backups with no protected copy, a Defender alert nobody receives, an emergency path that fails during an incident, a standing Owner assignment misused, a VM with RDP or SSH open to the internet, a purged key vault, missing activity and resource logs, runaway spend after credential compromise, and a subscription transferred out of or into the directory. No row describes a real organization, tenant, or incident.

Each row's `related_controls` field names the control ids from [desired-state.json](desired-state.json) that would reduce it. Likelihood and impact use the library's 1 to 3 scale and bands from the [risk assessment and treatment method](../../documentation/cyber-risk/risk-assessment-and-treatment.md): 1 to 2 Low, 3 to 4 Moderate, 6 High, 9 Critical. The inherent rating describes the scenario with none of the related controls in place. The residual rating assumes every related control operates and is evidenced, which in assessment terms means each related control shows `aligned`. If any related control is a gap or unknown, the residual rating has not been earned and the inherent rating stands until evidence arrives.

Every row is `Proposed`, with `Unassigned` and `Pending` placeholders for dates, verification evidence, and acceptance authority. The columns extend the [library risk register template](../../library/templates/risk-register.csv) with threat source, affected assets, related controls, and written ratings so the register and the baseline can be read together. Replace the scenarios, agree the scoring with the sponsor, and keep the completed register in the firm's protected record.

## The first review session

Run the [fictional example](observed.example.json) with the [local assessment tool](../README.md):

```sh
node baselines/scripts/assess.mjs baselines/azure/desired-state.json baselines/azure/observed.example.json --as-of 2026-09-29
```

It reports 7 aligned, 3 gaps, 88 unknown, and 1 not applicable. The twenty observations include a stale observation, a missing evidence reference, two paid capabilities the fictional firm has not bought, two values recorded as unknown, an applicability not yet established, two partial scopes, an approved exception that still shows as a gap, and a scoped not-applicable control; the other 79 controls have no observation and assess as unknown. Every value in it is invented.

For a real review, copy the worksheet and the risk template outside the repository and choose five priority questions: who can elevate to root scope and whether anyone would notice, who holds standing Owner on each subscription, whether a leaked workload secret would be noticed before the invoice, whether any storage account, VM, or database accepts traffic from the whole internet, and whether a backup can be restored without depending on an administrator or a key that might be gone. Record uncertainty as unknown. Then use the [staged rollout plan](../rollout-and-exceptions.md) to turn evidence into specific, reversible changes.
