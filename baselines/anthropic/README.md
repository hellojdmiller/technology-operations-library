# Anthropic: a baseline for technology operations

I would start with what a small firm cannot afford to lose on this platform: control of who is inside the organization, and control of where firm data goes once Claude can read it. On Claude that means the identity path into claude.ai and the Console, the sharing and retention settings on chats, projects, and artifacts, the connectors and extensions that reach mail and files, the instructions every conversation starts from, and the API keys and agents that act without a person watching. A useful baseline protects those paths while still letting the deal team, finance, and engineers use Claude every day.

This guide is a proposed operating standard. [Eighty control assertions](desired-state.json), the [evidence worksheet](evidence-worksheet.csv), and a [risk assessment template](risk-assessment.csv) make it reviewable. They are not settings to import, and the [local assessment tool](../README.md) compares reviewer-recorded assertions; it does not connect to Anthropic, read an organization, or verify evidence. The linked Anthropic documentation was reviewed on **2026-09-29**; each control carries its own source and a review gate that names the plan or product it depends on.

## Make the scope explicit

Before rating any setting, record the claude.ai plan (Team, or Enterprise and whether it is seat-based or usage-based), whether a parent organization links claude.ai and Console organizations, the Console usage tier and workspaces, who holds Claude Code seats, which devices get Claude Desktop and Claude Code policy through MDM, whether Claude in Chrome or Cowork is in use, the identity provider, and any client obligations on retention, residency, or training. Many controls here are Enterprise only; on Team the review gate says what to record instead. Keep the actual details outside this repository.

Use three example populations when designing a pilot: an Owner who administers the organization, a deal or research user who works with connectors and shared projects, and a developer who runs Claude Code or an API workload. Include a contractor on a firm address if that is an actual requirement. The purpose is to expose a business dependency before an organization-wide restriction does.

## Identity and membership: controls 01–14

SSO is available on Team, Enterprise, and Console organizations through a SAML flow run by WorkOS, after domain verification. Requiring SSO is a separate toggle for Claude and for the Console, and the default leaves email sign-in open. Requiring it makes personal accounts on the domain that are not in the SSO app inaccessible, and an expired IdP certificate locks everyone out until Support steps in, so record the expiry date. Restrict organization creation stops new organizations and personal accounts on the verified domain. [Set up single sign-on (SSO)](https://support.claude.com/en/articles/13132885-set-up-single-sign-on-sso), [considerations before enabling SSO](https://support.claude.com/en/articles/10276682-important-considerations-before-enabling-single-sign-on-sso-and-jit-scim-provisioning).

Provisioning defaults to Invite only. JIT is available on every plan; SCIM only on Enterprise and qualifying Console organizations. Under JIT, unassigning someone in the IdP blocks sign-in but leaves them in the member list with a seat, so a leaver exercise has to prove the manual removal. Group mappings drop Owners and Admins who are not in a mapped group; only the single Primary Owner is exempt. [Set up JIT or SCIM provisioning](https://support.claude.com/en/articles/13133195-set-up-jit-or-scim-provisioning), [Manage members on Team and Enterprise plans](https://support.claude.com/en/articles/13133750-manage-members-on-team-and-enterprise-plans).

Domain capture is Enterprise only and cannot be reversed; I treat it as a decision with a change record rather than a setting to flip. Discoverability, member-to-member invites, and invite links all default to on for new Team organizations and all let people in without an admin choosing them. [Claim and migrate accounts on your domain](https://support.claude.com/en/articles/14625619-claim-and-migrate-accounts-on-your-domain), [Find and join a Team or Enterprise organization](https://support.claude.com/en/articles/13566435-find-and-join-a-team-or-enterprise-organization).

Roles decide who can change everything else. One Primary Owner exists per organization and can be a service account; Owners manage roles and, on Enterprise, SSO. An Enterprise custom role with Identity & Access set to Manage can edit its own role, so reserve it. In the Console, Developer and Limited Developer can create API keys and Admin becomes Workspace Admin everywhere. [Roles and permissions](https://support.claude.com/en/articles/9267276-roles-and-permissions), [Set up role-based permissions on Enterprise plans](https://support.claude.com/en/articles/13930458-set-up-role-based-permissions-on-enterprise-plans), [Claude Console roles and permissions](https://support.claude.com/en/articles/10186004-claude-console-roles-and-permissions).

## Network access: controls 15–16

Tenant Restrictions let the firm's proxy inject `anthropic-allowed-org-ids` so that, on the corporate network, only the firm's organizations work for web, desktop, API key, and OAuth access. It is documented for Enterprise and Console organizations and needs TLS inspection. IP allowlisting is Enterprise only and set up through Support; the page does not say which surfaces it covers, so test each one. [Enforce network-level access control with Tenant Restrictions](https://support.claude.com/en/articles/13198485-enforce-network-level-access-control-with-tenant-restrictions), [Restrict access to Claude with IP allowlisting](https://support.claude.com/en/articles/13200993-restrict-access-to-claude-with-ip-allowlisting).

## Data, training, and retention: controls 17–24

For commercial products Anthropic states it will not train on chats or coding sessions unless the customer joins the Development Partner Program. Personal accounts are different: consumer chats may be used for training when the user allows it or a chat is flagged, which is why ANT-18 is a written rule for staff rather than a setting. [How do you use personal data in model training?](https://privacy.claude.com/en/articles/7996885-how-do-you-use-personal-data-in-model-training), [Is my data used for model training?](https://privacy.claude.com/en/articles/10023580-is-my-data-used-for-model-training).

Enterprise custom retention applies separately to chats and to projects, and project retention wins for chats inside a project; the default is indefinite. It does not reach Claude Design, Claude Tag, Managed Agents, or features built on Claude Code on the web. On Team there is no custom retention, so record it as unsupported. [Configure custom data retention controls for Enterprise plans](https://support.claude.com/en/articles/10440198-configure-custom-data-retention-controls-for-enterprise-plans), [How long do you store my organization’s data?](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data).

On the API, zero data retention is arranged per organization through sales and does not cover the Console, the Team and Enterprise interfaces, or flagged content. The API does not block ZDR-ineligible features such as code execution, the Files API, or the MCP connector; using one steps outside the arrangement. Inference geo defaults to global; a workspace can restrict it to US. Claude Code keeps plaintext local transcripts for 30 days unless `cleanupPeriodDays` says otherwise. [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention), [Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency), [Data usage](https://code.claude.com/docs/en/data-usage).

## Sharing: controls 25–28

Public projects here means visible to everyone in the organization, and it is on by default; turning it off makes existing public projects private. On Enterprise, project sharing can be granted by role. Team and Enterprise members can share chats only inside the organization. [Control project sharing for your organization](https://support.claude.com/en/articles/9927533-control-project-sharing-for-your-organization), [Roles and permissions](https://support.claude.com/en/articles/9267276-roles-and-permissions).

Artifacts have two separate outside-sharing settings: External sharing for anyone with the link and Email invitations outside your organization. The page does not state their defaults. Turning them off also stops existing outside access, which is useful after an incident. [Artifacts admin guide for Team and Enterprise plans](https://support.claude.com/en/articles/16994751-artifacts-admin-guide-for-team-and-enterprise-plans).

## Features: controls 29–34

Code execution and file creation runs in a sandbox, but with egress on, a prompt injection can send data out. The safest option is egress off; All domains is the riskiest. The same page gives two different Team defaults, so check the actual setting. MCP connectors can still move data whatever the egress setting says. [Create and edit files with Claude](https://support.claude.com/en/articles/12111783-create-and-edit-files-with-claude).

Memory is off by default on Team and Enterprise, and turning it off later deletes everyone's memory. Skills publishing on Team starts Open, meaning anything a member publishes reaches everyone; Requires review puts an Owner in the path, and Enterprise adds malware scanning. [Use Claude’s chat search and memory to build on previous context](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context), [Provision and manage skills for your organization](https://support.claude.com/en/articles/13119606-provision-and-manage-skills-for-your-organization).

Claude in Chrome reads and acts on web pages in the user's browser. It is on by default for Team and turns on by default for Enterprise from September 10, 2026. Anthropic describes classifiers and blocked categories and says the risk is not zero; I would start with a pilot and a restrictive site allowlist. [Claude in Chrome admin controls](https://support.claude.com/en/articles/13065128-claude-in-chrome-admin-controls), [Use Claude in Chrome safely](https://support.claude.com/en/articles/12902428-use-claude-in-chrome-safely).

## Integrations: controls 35–39

Connectors inherit each user's permissions in the source system, and an Owner decides which ones the organization can use. Custom remote MCP connectors are added only by Owners on Team and Enterprise, run from Anthropic's cloud, and are not verified by Anthropic. Tool permissions let an Owner set write tools to Needs approval or Blocked for everyone. The verified-domain restriction (Enterprise) stops a personal Claude account connecting a firm mailbox, but does not disconnect existing connections. The desktop extension allowlist is off by default. [Use connectors to extend Claude's capabilities](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities), [Get started with custom connectors using remote MCP](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), [Restrict verified-domain connectors to your Enterprise](https://support.claude.com/en/articles/15402193-restrict-verified-domain-connectors-to-your-enterprise), [Enabling and using the desktop extension allowlist](https://support.claude.com/en/articles/12592343-enabling-and-using-the-desktop-extension-allowlist).

## Claude Desktop: controls 40–44

Claude Desktop reads policy from `com.anthropic.claudefordesktop` on macOS and `HKLM\SOFTWARE\Policies\Claude` on Windows. The security keys are the extension switches, local MCP servers, Cowork folders, the organization pin, and updates. Machine policy overrides the in-app allowlist, so setting the extension keys to false stops the allowlist working. [Enterprise configuration for Claude Desktop](https://support.claude.com/en/articles/12622667-enterprise-configuration-for-claude-desktop).

## Master instructions: controls 45–53

JD asked about "master instructions". This baseline reads the term as the governance of organization-wide instructions: who may set workspace-level or project-level instructions (and project instructions, Claude Code policy files and managed settings, repository instruction files such as AGENTS.md or CLAUDE.md, and API system prompts), how they are reviewed and versioned, and whether members can override them.

On claude.ai, organization instructions are set by Owners, apply to every conversation, and win over a member's own instructions, but only at the prompt level; they are guidance, not enforcement. There is no version history on the page, so the text belongs in version control. [Set organization instructions](https://support.claude.com/en/articles/14546867-set-organization-instructions), [Understanding Claude's personalization features](https://support.claude.com/en/articles/10185728-understanding-claude-s-personalization-features).

Claude Code policy is the enforceable part. Server-managed settings are edited only by Owners and fetched hourly, but the page calls them a client-side control, not a security boundary, so pair them with MDM or file policy and set `forceRemoteSettingsRefresh`. HKCU is not an enforcement channel. The managed CLAUDE.md cannot be excluded, and `allowManagedPermissionRulesOnly` stops members adding their own allow rules. Repository instruction files and API system prompts are process controls: review them like code. [Configure server-managed settings](https://code.claude.com/docs/en/server-managed-settings), [Deploy managed settings](https://code.claude.com/docs/en/managed-settings), [Set up Claude Code for your organization](https://code.claude.com/docs/en/admin-setup), [How Claude remembers your project](https://code.claude.com/docs/en/memory), [Computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool).

## Claude Code and agents: controls 54–69

These keys belong in managed settings. Disable bypassPermissions, which is meant for isolated containers only; decide on auto mode, which is now the built-in starting mode; deny reads of secret files; run only managed hooks; allowlist MCP servers by URL or command, since a server name is not a security control; and turn on the sandbox with fail-closed startup, no unsandboxed retry, and managed domains only. The sandbox does not run on native Windows. Restrict plugin marketplaces, reject sideload flags, and pin logins to the firm organization through MDM, because server-managed settings cannot redirect a first login. [Choose a permission mode](https://code.claude.com/docs/en/permission-modes), [Configure permissions](https://code.claude.com/docs/en/permissions), [Control MCP server access for your organization](https://code.claude.com/docs/en/managed-mcp), [Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing), [Authentication](https://code.claude.com/docs/en/iam), [All settings](https://code.claude.com/docs/en/settings-reference).

Owners switch Remote Control and cloud sessions on or off for the organization. Cloud environments default to Trusted network access; Full is the one to approve. For firm applications using the computer use tool, Anthropic's precautions are a dedicated VM or container, no credentials, a domain allowlist, and human confirmation. [Deploy managed settings](https://code.claude.com/docs/en/managed-settings), [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments), [Security](https://code.claude.com/docs/en/security), [Computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool).

An agent that can read mail, run code, or drive a browser is a tool with authority. The library's [agent and MCP controls](../../cyber-risk/ai/agent-and-mcp-controls.md) describe how to record authority at each boundary, and the [agent security lab](../../labs/agent-security/README.md) shows how to test that a scope change or interrupted tool call is handled by deterministic controls rather than by trusting the model. Neither replaces the platform controls here; together they explain why ANT-37, ANT-54, ANT-58, and ANT-60 matter more once an agent holds a token.

## Console and API: controls 70–77

Each usage tier has a monthly spend cap, and the firm can set a lower limit; workspaces can carry their own spend and rate limits, except the Default Workspace. Team and Enterprise usage credits let members go past the seat allowance, so cap them. [Rate limits](https://platform.claude.com/docs/en/api/rate-limits), [Workspaces](https://platform.claude.com/docs/en/manage-claude/workspaces), [Manage costs effectively](https://code.claude.com/docs/en/costs).

Personal and service account keys stop working when their identity leaves; legacy workspace keys do not. Expiration is fixed at creation and Never is offered unless an organization policy removes it; the pages do not say where that policy is set. Workload Identity Federation removes static keys for automated workloads. Admin API keys have no scopes and full access. Disable is reversible, Delete is permanent, and GitHub secret scanning only covers public repositories. [Authentication](https://platform.claude.com/docs/en/manage-claude/authentication), [Create an Admin API key](https://platform.claude.com/docs/en/manage-claude/admin-api-keys), [Admin API](https://platform.claude.com/docs/en/manage-claude/admin-api), [API Key Best Practices: Keeping Your Keys Safe and Secure](https://support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure).

## Monitoring: controls 78–80

Audit log export is Enterprise only, covers 180 days, and the link lasts 24 hours, so a monthly export is what keeps evidence. Only the Primary Owner can enable the Compliance API, which excludes cloud sessions and third-party cloud sessions. Enterprise API key scopes are fixed at creation; give each integration only what it needs. [Access audit logs](https://support.claude.com/en/articles/9970975-access-audit-logs), [Access the Compliance API](https://support.claude.com/en/articles/13015708-access-the-compliance-api), [Create an Admin API key](https://platform.claude.com/docs/en/manage-claude/admin-api-keys).

Candidates that are not in the table, and why:

* Chat sharing: Team and Enterprise members can share chats only inside the organization, and no admin toggle was documented on the page read.
* Incognito chats and research: available to members, with no admin toggle documented. Incognito chats are kept 30 days on Team and Enterprise and appear in exports.
* Web search: an Owner must turn it on, but it retrieves rather than publishes, so I did not make it a control; research needs it.
* Sensitive topics in memory, artifact templates, artifact connectors, 1Password for Claude, and Cowork settings: documented, but either covered by a stronger control above or outside this scope.
* File uploads: no admin control and no plan difference is documented.
* Allowed models per Console workspace: the model configuration page says the Console has no model restriction control; Enterprise model restrictions and `availableModels` exist but are not security controls in this baseline.
* Verified-domain connector restriction and Tenant Restrictions: these are restrictions to turn on, so they appear as controls ANT-38 and ANT-15 rather than in this table.

## Risk scenarios

The [risk assessment template](risk-assessment.csv) lists eleven generic scenarios for this platform, from a leaked Console API key to audit evidence that ages out before an investigation. Each row names the threat source, affected assets, and the control ids in `related_controls` that would reduce it. Ratings use the 1 to 3 likelihood and impact scale and bands from the library's [risk assessment and treatment report](../../documentation/cyber-risk/risk-assessment-and-treatment.md): 1 to 2 Low, 3 to 4 Moderate, 6 High, 9 Critical. Inherent ratings describe the scenario before controls; residual ratings assume every related control operates with fresh evidence.

The two files work together. A residual rating in the template only holds when the assessment shows each related control as aligned. If one is a gap or unknown, treat the inherent rating as current and record that in the private register. Every row is `Proposed`, with `Unassigned` and `Pending` placeholders for dates, evidence, and acceptance authority; no scenario describes a real organization or incident. The columns extend the [sanitized register schema](../../library/templates/risk-register.csv) with threat source, assets, related controls, and computed rating text.

## The first review session

Run the [fictional example](observed.example.json) with the [local assessment tool](../README.md) at `--as-of 2026-09-29`; it produces seven aligned assertions, three gaps, sixty-nine unknowns, and one scoped non-applicable control. The fictional firm has a claude.ai Team plan, a Console organization on the Build tier, and Claude Code on Team seats. Its unknowns include two Enterprise-only features recorded as unsupported, a stale observation, a future-dated observation, missing evidence, a partial device sample, an unestablished applicability, an unknown mechanism, and a value the reviewer could not confirm; sixty others have no observation at all. One gap, Claude in Chrome left at the Team default, carries an approved exception and still shows as a gap. Workload Identity Federation is excluded because the fictional inventory has no automated API workload.

For a real review, copy the worksheet outside the repository and choose five priority questions: who can administer the organization and its SSO if an Owner leaves, where firm data can leave through sharing, connectors, or egress, which instructions and policies every session starts from and who changed them last, which keys and agents can act without a person, and whether audit evidence will still exist when it is needed. Record uncertainty as unknown rather than guessing. Then use the [staged rollout plan](../rollout-and-exceptions.md) to turn each gap into a reviewed change with a pilot, a stop condition, and a rollback.
