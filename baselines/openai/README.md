# OpenAI: a baseline for technology operations

I would start with what a small firm cannot afford to lose on this platform: control over which people and agents can reach firm data through ChatGPT, and which credentials can run models or Codex without a person watching. In a ChatGPT workspace used for research, drafting, and multi-step Work tasks, and an API organization used for internal tools, those paths run through the identity provider, workspace roles, plugins and their connections, local agent policy, tokens, and API keys. A useful baseline protects them while still letting people use Work, Codex, and the API for real work.

This guide is a proposed operating standard. [Eighty control assertions](desired-state.json), the [evidence worksheet](evidence-worksheet.csv), and a [risk assessment template](risk-assessment.csv) make it reviewable. They are not settings to import, and the [local assessment tool](../README.md) compares reviewer-recorded assertions; it does not connect to ChatGPT or the API platform, read a workspace, or verify evidence. The linked OpenAI documentation was reviewed on **2026-09-29**; each control carries its own source and a review gate that names the plan or product it depends on and the documented default where one is stated.

## Make the scope explicit

Before rating any setting, record the ChatGPT plan for each workspace (Business, formerly Team; Enterprise; or Edu), whether Work Cloud and Work Local appear as separate permissions, the seat types in use, whether the plan is pay-as-you-go (service accounts depend on it), and which add-ons exist: Compliance API, Enterprise Key Management, Prisma AIRS. For the API platform, record each organization and project, the billing arrangement, and any approval for Zero Data Retention, Modified Abuse Monitoring, or data residency. Record the identity provider, whether SSO and SCIM are available on the plan, where MFA is enforced, the MDM tool, and the Codex client versions on managed devices. Keep the actual details outside this repository.

Use three example populations when designing a pilot: a workspace owner, a member who uses Work with connected mail and files, and a developer who runs Codex locally and in the cloud with at least one automation token. Include an API workload with its own project if the firm has one. The purpose is to expose a business dependency before a workspace-wide restriction does.

## Identity and roles: controls 01–06

ChatGPT does not enforce MFA workspace-wide. Members can turn on account-level MFA, and OpenAI says organizations that require it should enforce SSO and MFA through their identity provider. I would treat the identity provider as the only sign-in door and test a synthetic member's MFA prompt. Codex cloud requires MFA for email and password accounts on its own. [ChatGPT Work admin FAQ](https://learn.chatgpt.com/docs/enterprise/work-admin-faq), [Authentication](https://learn.chatgpt.com/docs/auth).

SCIM Directory Sync is documented for Enterprise, Edu, and Healthcare, not Business. OpenAI says not to run Automatic Account Creation alongside SCIM, because accounts created on sign-in might not be SCIM-managed and can survive removal from the identity-provider group. For a SCIM-managed leaver, removal belongs in the identity provider: a workspace-side removal can be undone by the next sync. On Business, a monthly member review against the HR roster does that job. [User lifecycle management](https://learn.chatgpt.com/docs/enterprise/user-lifecycle), [Groups and provisioning](https://learn.chatgpt.com/docs/enterprise/groups-and-provisioning).

The built-in roles are Owner, Admin, Member, and Analytics Viewer. Owners alone configure RBAC, create custom roles, and grant access-token permission, so the owner list is the most sensitive list here. Custom roles use Default, On, and Off, and an explicit Off in any assigned role wins over On in another. They exist on Enterprise, Edu, Healthcare, and Teachers, not Business. [Roles and workspace permissions](https://learn.chatgpt.com/docs/enterprise/roles-and-workspace-permissions).

## ChatGPT Work access: controls 07–13

Work Cloud runs hosted multi-step tasks that can reach connected systems. For eligible Enterprise and Edu workspaces, the default role includes Work unless an administrator turns it off, so I would switch the default off and grant it to a pilot group. Local Work and Codex access sit under Codex and Work Local, or under separate Codex Local and Work Local sections; enabling one separate control does not grant the other. [ChatGPT Work admin FAQ](https://learn.chatgpt.com/docs/enterprise/work-admin-faq), [ChatGPT Work cloud security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-cloud-security), [ChatGPT Work local security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-local-security).

The cloud browser is a separate tool. In Enterprise an administrator must enable it in addition to Work, and website sign-in through it is not available in Enterprise or Edu. By default ChatGPT asks before visiting a new website; users can choose Always ask, Auto approve, or Always allow, and administrators can disable Always allow workspace-wide. OpenAI itself does not recommend Always allow. Public internet access for Work code and shell commands is a separate network setting again; turning it off leaves a managed allowlist of required destinations and does not turn off web search, apps, or the browser. [ChatGPT Work Overview](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-overview), [Browser](https://learn.chatgpt.com/docs/browser).

Computer History is off by default for Business and Enterprise workspaces and needs an owner to grant it by role before a member can opt in. It turns activity across apps and websites into memories, including communication apps, and its local files are not encrypted by Computer History. I would leave it ungranted. [Computer History](https://learn.chatgpt.com/docs/customization/computer-history).

New models arrive off in Enterprise: GPT-6 Sol and Luna need an administrator to enable each, and Astra needs Daybreak access. GPT-5.5 retires from ChatGPT, Work, and Codex on October 14, 2026, so replace it in workspace defaults and managed configuration. A workspace model setting does not automatically carry over to Codex clients, Codex cloud, or the API. [Workspace model availability](https://learn.chatgpt.com/docs/enterprise/workspace-model-availability).

## Plugins, apps, and connections: controls 14–21

A plugin can bundle skills, MCP servers, and hooks, and each layer has its own control: availability per role, MCP server access in Workspace apps, Action control, App permissions, and the connected account's own authorization. The pages disagree on the starting state. The Work overview says plugins and their apps are off by default for Enterprise and Edu and on for Business; the local-security page says new Enterprise and Edu workspaces start with a selected set of apps enabled. Inspect the actual workspace and record it rather than assuming either. [Plugin controls](https://learn.chatgpt.com/docs/enterprise/apps-and-connectors), [ChatGPT Work Overview](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-overview), [ChatGPT Work local security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-local-security).

Action control can allow all actions, read-only actions, or a custom set, and decides how newly added actions are handled. App permissions decide when ChatGPT asks: Always ask, Any changes, Important actions, or Never ask. OpenAI recommends starting with read actions. A shared or agent-owned connection acts with the connected account's permissions, which can exceed what the requesting member could reach, so each one needs an owner, narrow scopes, and a restricted audience. [ChatGPT Work cloud security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-cloud-security).

A GitHub marketplace import syncs daily by default, adds every new plugin in the repository, and starts new plugins as Available. Pinning to a fixed commit or protecting the source branch keeps an unreviewed merge from becoming a workspace plugin. Upload plugins with custom MCP servers and Publish plugins to workspace are separate permissions in the Enterprise admin guidance and belong to named maintainers. Skills follow the same principle; the skill controls page describes separate ownership for workspace skills, filesystem skills, and plugin-bundled skills, which is why I left them to the plugin register rather than a separate control. [Plugin management](https://learn.chatgpt.com/docs/enterprise/plugin-management), [Moving your custom GPT workflows to plugins](https://learn.chatgpt.com/docs/migrate-custom-gpts), [Skill controls](https://learn.chatgpt.com/docs/enterprise/skills).

## Sharing and publishing: controls 22–26

The GPTs admin page controls who can create GPTs, whether they can be shared with people, groups, or the whole workspace, and which external domains GPT actions may call. If no domains are allowed, custom GPT actions cannot run. OpenAI is moving custom GPT workflows to plugins, and bulk migration does not copy sharing settings, so record each GPT's audience before migrating. [GPTs and Sharing](https://learn.chatgpt.com/docs/enterprise/gpts-and-sharing), [Moving your custom GPT workflows to plugins](https://learn.chatgpt.com/docs/migrate-custom-gpts).

A new Site is limited to its owner and workspace admins. In Enterprise, public publishing is off by default and must be enabled by an admin, and Allow members to invite external visitors to sites is a separate permission. Business has no separate external-invitation toggle. A public Site is reachable without workspace access. [Sites](https://learn.chatgpt.com/docs/sites).

## Data handling: controls 27–31

Administrators can control whether ChatGPT automatically references saved Library files; turning it off does not stop members attaching files they may use. Enterprise and Edu chats, files, and canvas documents follow the configured retention policy, while Business keeps them indefinitely. Retention differs by data type: Library files, project files, memories, transient uploads, and compliance records each follow their own rules. Enterprise Key Management covers supported stored content on eligible Enterprise and Edu workspaces, and a rotation does not delete data. [ChatGPT Work Overview](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-overview), [ChatGPT Work cloud security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-cloud-security), [User lifecycle management](https://learn.chatgpt.com/docs/enterprise/user-lifecycle).

Prisma AIRS scans newly submitted Codex prompts, not responses, tool calls, files, or images, and not API-key sessions. Its enforcement mode defaults to Block, but On AIRS failure defaults to Allow prompts, so an outage lets prompts through unscanned. I would set it to Block prompts where the firm depends on the scan. [Prisma AIRS](https://learn.chatgpt.com/docs/enterprise/prisma-airs).

## Automation credentials: controls 32–35

Codex access tokens are supported on Business and Enterprise and act as the member who creates them. Only an owner grants the permission, and an owner can cap the lifetime of new tokens; existing tokens keep their window, and an earlier Codex-only dialog can still offer No expiration. Removing a member's local Codex permission suspends their tokens rather than revoking them, and restoring it brings them back, so a leaver's tokens need an explicit revoke. Service accounts give a durable automation its own identity and are available only on pay-as-you-go plans. [Access tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens), [Service accounts](https://learn.chatgpt.com/docs/enterprise/service-accounts), [User lifecycle management](https://learn.chatgpt.com/docs/enterprise/user-lifecycle).

## Codex managed requirements: controls 36–50

`requirements.toml` holds constraints users cannot override, delivered through the system file, cloud-managed requirements on a supported ChatGPT sign-in, or macOS MDM. An omitted key constrains nothing, which is the documented default for every control in this section. Each key is its own control because each one closes a different path: `allowed_approval_policies` without `never`; `allowed_permission_profiles` without `:danger-full-access` (Codex 0.138.0 or later), and `allowed_sandbox_modes` without `danger-full-access` for older deployments; `allowed_web_search_modes` without `live`; an `mcp_servers` allowlist matched by name and identity; and restrictive `[rules]`. [Managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration), [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security).

Login restrictions are different: `allowed_login_methods` and `allowed_chatgpt_workspaces` are ignored in cloud-managed requirements and must be set in the local system file or MDM. The workspace allowlist also applies to Codex access tokens. The desktop feature keys are separate surfaces: `features.computer_use` (which also disables Record & Replay), `features.browser_use`, `features.browser_use_external` for the extension that acts in real signed-in tabs, `features.plugins`, `allow_appshots`, `allow_remote_control`, and `computer_use.allow_locked_computer_use`, which removes the option but does not turn off Locked Use already enabled. Computer Use operating a browser is not covered by Browser Use site policies. [ChatGPT Work local security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-local-security), [Computer Use](https://learn.chatgpt.com/docs/computer-use).

Managed network requirements under `[experimental_network]` exist but are marked experimental, with limited Windows support, so I have not made them a control; test them on the actual fleet first. An agent with a token or a connection is a tool with write authority. The library's [agent and MCP controls](../../cyber-risk/ai/agent-and-mcp-controls.md) describe how to record authority at each boundary, and the [agent security lab](../../labs/agent-security/README.md) shows how to test that a scope change or interrupted tool call is handled by deterministic controls rather than by trusting the model. Neither replaces the platform controls here; together they explain why OAI-36, OAI-37, OAI-40, and OAI-43 matter more once an agent holds a credential.

## Codex cloud environments: controls 51–54

Codex cloud blocks internet access during the agent phase by default; setup scripts still have it. Access is set per environment, with presets of None, Common dependencies, and All (unrestricted), and requests can be limited to GET, HEAD, and OPTIONS. OpenAI names prompt injection, code or secret exfiltration, and malicious dependencies as the risks. Secrets are removed before the agent phase and environment variables are not, and Business and Enterprise caches are shared across users of an environment. [Agent internet access](https://learn.chatgpt.com/docs/cloud/internet-access), [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment).

## Master instructions: controls 55–60

JD asked about "master instructions". I read the term as the governance of organization-wide instructions: who may set workspace-level or project-level instructions (and custom GPT or plugin instructions, Codex policy files and managed settings, repository instruction files such as AGENTS.md, and API system prompts), how they are reviewed and versioned, and whether members can override them. OpenAI has no single setting for this, so most controls here are manual, but each one governs a mechanism the cited page documents.

Each managed policy should have a named owner, audience, and business reason, and OpenAI advises treating the managed TOML like any other MDM setting under change control. Security settings belong in requirements, which users cannot override, rather than in managed defaults, which users can change during a run. `additional_developer_instructions` adds a managed developer message to every Codex session and is the closest thing to a firm-wide system prompt for Codex, so its text should be reviewed like code; the automatic review policy in `guardian_policy_config` is governed the same way. [Managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration), [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference).

Codex reads a global AGENTS.md from the Codex home directory and then project files from the repository root down, with later files taking precedence, and `AGENTS.override.md` can replace guidance at any level. The default sandbox keeps `.git`, `.agents`, and `.codex` read-only, but a pull request can still change them, so they need required review. For the API, OpenAI advises treating prompts as application code, and `v1/prompts` is scheduled to shut down on November 30, 2026. GPT and plugin instructions are covered by the creation, sharing, and publishing controls above. [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security), [Prompting](https://developers.openai.com/api/docs/guides/prompting).

## API platform: controls 61–76

The API platform is a separate boundary: ChatGPT roles do not reach it. Grant access through groups and custom roles, with groups synced by SCIM where the identity provider supports it; access from several roles is a union, and changes take up to 30 minutes. The changelog records self-serve SSO for Enterprise customers on custom and unlimited billing. [Manage permissions in the OpenAI platform](https://developers.openai.com/api/docs/guides/rbac), [Changelog](https://developers.openai.com/api/docs/changelog).

API Key Governance can allow only service-account keys, only user-owned project keys, or no new keys, and organization restrictions win over projects. A maximum key lifetime makes new keys expire; neither setting changes existing keys. Workload identity federation removes stored keys for workloads that already hold an identity-provider token, and mutual TLS enforces client certificates once a trust anchor is activated. An IP allowlist applies only to API requests, project lists replace the organization list rather than combining with it, and Private Link is not compatible with either IP allowlists or mTLS. [Production best practices](https://developers.openai.com/api/docs/guides/production-best-practices), [Workload identity federation](https://developers.openai.com/api/docs/guides/workload-identity-federation), [Mutual TLS](https://developers.openai.com/api/docs/guides/mutual-tls), [IP allowlist](https://developers.openai.com/api/docs/guides/ip-allowlist), [Private Link](https://developers.openai.com/api/docs/guides/private-link).

Project controls limit which models a project may call and which hosted tools it may use: file search, web search, image generation, remote MCP, and Code Interpreter. A project cannot disable a tool the organization enables for every project. Spend alerts notify but do not cap; a hard spend limit returns 429 errors once reached. Admin API keys manage users, keys, limits, and retention, and audit logging must be enabled in settings. [Model, tool, and data controls with Terraform](https://developers.openai.com/api/docs/guides/terraform/project-controls), [Spend limits](https://developers.openai.com/api/docs/guides/spend-limits), [Admin APIs](https://developers.openai.com/api/docs/guides/admin-apis).

Abuse-monitoring logs are kept for up to 30 days by default. Zero Data Retention and Modified Abuse Monitoring require approval and can be set per project, but ZDR does not cover application state stored by ineligible endpoints such as assistants, threads, vector stores, files, and batches; files can be given an `expires_after`. Data residency is chosen when a project is created. The moderation endpoint is free, and `safety_identifier` lets OpenAI trace abuse to one end user. [Data controls in the OpenAI platform](https://developers.openai.com/api/docs/guides/your-data), [Moderation](https://developers.openai.com/api/docs/guides/moderation), [Safety best practices](https://developers.openai.com/api/docs/guides/safety-best-practices).

## Monitoring: controls 77–78

For eligible Enterprise and Edu workspaces, the Compliance Logs Platform holds records for 30 days, so continuous export is the only way to keep them longer. Coverage does not include every shell command, browser action, or approval. Codex OpenTelemetry export is off by default and redacts prompt text unless `otel.log_user_prompt = true`; keep it false and send events to a collector the firm controls. [Compliance API and audit events](https://learn.chatgpt.com/docs/enterprise/compliance-api), [ChatGPT Work admin FAQ](https://learn.chatgpt.com/docs/enterprise/work-admin-faq), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security).

## Spend: controls 79–80

Eligible Enterprise and Edu workspaces set monthly per-user credit limits through a workspace default, group defaults, and overrides; Business follows a separate credit model. The overage limit is set separately in the Global Admin Console, alerts do not stop spending, and No limit is not a zero-spend cap. [ChatGPT Work: usage and cost](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-usage-and-cost).

## Risk scenarios

The [risk assessment template](risk-assessment.csv) lists twelve generic scenarios for this platform, from a leaked API key or Codex token to an agent running with approvals bypassed. Each row names the threat source, affected assets, and the control ids in `related_controls` that would reduce it. Ratings use the 1 to 3 likelihood and impact scale and bands from the library's [risk assessment and treatment report](../../documentation/cyber-risk/risk-assessment-and-treatment.md): 1 to 2 Low, 3 to 4 Moderate, 6 High, 9 Critical. Inherent ratings describe the scenario before controls; residual ratings assume every related control operates with fresh evidence.

The two files work together. A residual rating in the template only holds when the assessment shows each related control as aligned. If one is a gap or unknown, treat the inherent rating as current and record that in the private register. Every row is `Proposed`, with `Unassigned` and `Pending` placeholders for dates, evidence, and acceptance authority; no scenario describes a real workspace, organization, or incident. The columns extend the [sanitized register schema](../../library/templates/risk-register.csv) with threat source, assets, related controls, and computed rating text.

## The first review session

Run the [fictional example](observed.example.json) with the [local assessment tool](../README.md) at `--as-of 2026-09-29`; it produces seven aligned assertions, three gaps, sixty-nine unknowns, and one scoped non-applicable control. The fictional environment is a ChatGPT Business workspace with Codex and a pay-as-you-go API organization, so SCIM and custom roles show as unsupported. The unknowns also include a stale observation, missing evidence, an incomplete device scope, a future-dated record, an undecided applicability, and an unclear implementation; the gaps include an approved exception on user-owned API keys that still shows as a gap; and Locked Use is excluded because the fictional fleet has no Macs.

For a real review, copy the worksheet outside the repository and choose five priority questions: does removing someone at the identity provider end their workspace access and their Codex tokens, which plugins and shared connections can write to firm systems, can any agent run without approvals or with open internet, where would a leaked API key be stopped, and would a thirty-day compliance window cover the next investigation. Record uncertainty as unknown rather than guessing. Then use the [staged rollout plan](../rollout-and-exceptions.md) to turn each gap into a reviewed change with a pilot, a stop condition, and a rollback.
