# Using and adapting these examples

The adapted documents preserve useful policy, procedure, continuity, and risk-review structures from working material. They have been rewritten for a fictional investment firm. They are not facsimiles, approved policies, completed assessments, or evidence of a real organization's controls.

## What changed

Company and person names, contact details, domains, internal links, locations, tenant and asset identifiers, commercial terms, configuration inventories, incident history, and original approval records are omitted. Roles replace named people. Illustrative targets and examples are explicitly fictional.

The examples are newly authored Markdown. Original Word/PDF files, images, embedded objects, comments, tracked changes, and document metadata are not included. The source-to-example record is kept outside this repository.

Adaptation includes editorial and technical corrections. In particular, the examples separate a requested action from a verified result; treat recovery targets as assumptions until tested; distinguish a provider outage from recoverable data loss; and avoid carrying forward unsupported compliance or certification claims. The risk assessment uses wholly fictional findings and evidence references.

## Before using one internally

1. Select the document and identify the business owner, technical owner, approver, and audience.
2. Replace fictional assumptions with approved requirements. Keep sensitive implementation details in a protected annex or internal system.
3. Resolve missing platform, license, contractual, records, and legal questions with the responsible owners.
4. Test the operating procedure or control using a suitable isolated environment. Record expected and observed results separately.
5. Obtain the appropriate internal approval and set the effective date, review date, and change owner in the adopted copy.

## Adding another example to this repository

Work outside the repository until the content has been adapted and reviewed. Start a clean text document; do not copy a binary source and assume a name replacement removes its hidden content.

Review direct identifiers and combinations that could identify an organization: unusual system combinations, dates, locations, project names, financial figures, and recognizable incident narratives. Use synthetic cases where generalization would still reveal the original situation.

Check headings, tables, links, filenames, sample outputs, source code, comments, and commit content. Keep actual source files and the redaction/provenance record outside Git history. A search scan helps locate mistakes but cannot by itself prove anonymity.

This collection remains private for review. Public release requires a separate decision about the specific material, its rights, and its remaining disclosure risk.
