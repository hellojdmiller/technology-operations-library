# Build-versus-buy review

Work with the text, files, and tools actually available in the current environment. No particular provider, connector, or skill loader is required. If a referenced source cannot be inspected, keep it distinct from verified evidence.

Start with the workflow and the outcome people need. Translate product names or a preferred architecture into the capability being evaluated without discarding the user's constraints.

Use the supplied evidence to distinguish required capabilities, preferences, assumptions, and unknowns. Ask only for missing information that could materially change the recommendation; otherwise proceed with a visible assumption.

Compare plausible options: configure an existing platform, buy, combine a platform with a narrow extension, build, or simplify/defer. Leave out options that are clearly outside the user's scope, explaining the decisive constraint if useful. Evaluate options against the same acceptance conditions.

Consider who owns delivery, operation, support, access, recovery, data export, and eventual retirement. Separate one-time implementation effort from ongoing obligations. Faster development, including AI-assisted development, does not establish lower lifecycle cost. Do not invent cost estimates, quotations, delivery history, or an operating owner.

Where a decision depends on current vendor capabilities, pricing, or limits, verify them using available authoritative sources and record the date. If verification is unavailable, label the claim as unverified and identify the next check. A vendor description is a claim, not observed evidence in the user's environment.

Produce a concise decision memo that covers:

- The workflow, affected users, and required outcome.
- The material differences between feasible options.
- A recommendation, its assumptions, and the most consequential unknown.
- A small pilot with observable acceptance conditions and an owner to be assigned if unknown.
- What would change the recommendation, including operating burden and exit conditions.

Use plain language and explain the reasoning as a proposed approach. A weighted score is useful only when the user has a defensible weighting method; do not introduce arbitrary precision. Distinguish a recommendation from an approved decision. The review itself does not authorize purchases, deployment, or access changes.
